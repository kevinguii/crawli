01 · Foundations

Every account you opened, and what each key actually unlocked

You remembered Supabase, Resend, GSC and GA4. The real list was thirteen services. Here is the whole set, in roughly the order a rebuild should provision them, because several have hard ordering dependencies.

Provisioning order

  1. Domain + CloudflareTwo A records — @ and www — both to the origin IP. Cloudflare proxies (orange cloud) and terminates TLS at the edge; the origin also holds its own Certbot cert, which is what makes it Full (strict) rather than Flexible. The www host 301s to bare at nginx, not at Cloudflare.
  2. SupabaseProject first, because auth, DB, storage and every later table hang off it. Three keys, three different blast radii — see the wiring table below.
  3. ResendDomain verification before any key matters. SPF + DKIM records go in Cloudflare DNS. DMARC is the one you skipped, and it cost you (§09).
  4. StripeProducts and prices are provisioned by hand in the dashboard; code only ever reads price IDs out of env. Test mode first, live keys swapped in at the end.
  5. Google Search Console + GA4GSC verification via a meta tag (NEXT_PUBLIC_GSC_VERIFICATION) rendered by Next's metadata.verification. A service account (crawli-sa.json) then gets Full on GSC and Viewer on GA4 so scripts and MCPs can read both without you copy-pasting dashboards.
  6. SentryOrg + project, then npx @sentry/wizard, which writes the three config files and the SENTRY_AUTH_TOKEN used only at build time for source-map upload.
  7. UptimeRobotLast, because it needs live URLs to point at.

Pattern worth keeping

Every key sat in one .env on one box, and .env.example carried a paragraph of prose per variable explaining what it does, what breaks without it, and what the tradeoffs of each value are. That file was effectively the ops manual. Do it again.

02 · Architecture

Two processes, one box, and three clocks fighting over one semaphore

The single most consequential structural decision: the orchestrator and the browser engine are different processes in different languages, talking over localhost. Everything the project does — live search, alerts, the public SEO surface — runs through the same narrow gate.

  :3000  Next.js 16 (TypeScript)          :8000  Python sidecar (FastAPI)
  ─────────────────────────────          ────────────────────────────────
  auth, sessions, routing                Chromium via Playwright / crawl4ai
  API routes, NDJSON streaming           page render + extraction
  React 19 UI                            per-domain pacer, render semaphore
  Supabase reads/writes                  browser pool, TTLCache
  Firecrawl calls                        OpenAI via litellm (LLM fallback)
  Stripe, Resend                         anti-bot / stealth adapters

Why it was right. Scraping is a Python-ecosystem problem — crawl4ai, Playwright's Python bindings, the undetected-browser adapters have no real Node equivalent. Isolating them meant a Chromium crash killed the sidecar, not the web app: users saw degraded search, not a down site. The systemctl restart crawli-sidecar auto-heal (§11) only works because the two are separable.

Why it also hurt. Two runtimes, two dependency trees, two deploy paths, two sets of logs. The sidecar's in-memory caches and its per-domain pacer are per-process, which is precisely what caps you at one box — horizontal scaling needs Redis to move both out of process, and that refactor was specced but never needed.

The streaming protocol

/api/search returns NDJSON — newline-delimited JSON, one event per line, streamed as platforms finish rather than a single JSON body at the end. A search takes 7–35s; without streaming the UI is a spinner for half a minute. Events: platform_start, platform_done, final (with min/avg/max stats).

Scar tissue

Streaming endpoints buffer in next dev. You cannot test this in a browser devtools Network tab locally — it looks broken. The only real test is curl -N. This cost real hours before it was written down.

03 · Search engine

Avenue B, Avenue A, and the assumption that was never tested

The single biggest performance and cost win in the project came from deleting a whole pipeline, not from optimizing one.

Avenue B — the original design (retired 2026-08-25)

Ask Firecrawl for site:ebay.com <query> → get ~20 candidate URLs → regex-filter to listing-shaped URLs → scrape the first 10 individually through the sidecar. Cost: 4 Firecrawl credits per platform per search, ten renders, and heavy exposure to per-listing anti-bot.

Measured: 60.2s median, ~6 usable listings.

Avenue A — what replaced it

Build the platform's own search URL, render it once, extract the whole result grid. Zero Firecrawl credits. One render. No LLM.

Measured: ~7s, ~75 listings. Same platform. ~10× cheaper, ~8× faster, 12× more results.

The lesson that generalizes

eBay stayed on the expensive path for months on the belief that “Akamai blocking makes a native search-page render non-viable.” That belief was never tested. When it finally was, eBay's search page rendered fine, 8/8 concurrent, in 4.4s — it is the per-listing pages Akamai walls, which is exactly what the expensive path was doing ten of per search. An untested constraint hardened into architecture. Write down which of your assumptions are measured and which are inherited.

The fan-out

allSettledWithConcurrency(platforms, K=3)     K = SEARCH_PLATFORM_CONCURRENCY

  Round 1  [grailed] [depop] [poshmark]        ← 3 slots
  Round 2  [stockx]  [thredup]                 ← as slots free
      ↓
  each platform_done → NDJSON event → UI row flips to "Done — N results"

Three concurrency ceilings stack, deliberately: SEARCH_PLATFORM_CONCURRENCY=3 in Next, SIDECAR_MAX_CONCURRENT_RENDERS in Python (a real asyncio.Semaphore), and SIDECAR_BROWSER_POOL_SIZE Chromium processes sharing that semaphore. Plus a per-domain pacer that waits outside the semaphore — 400ms between Grailed hits, 300ms for eBay, 150ms otherwise — so a politeness delay never burns a render slot.

Why all of that exists

A bare Promise.all(platforms.map(...)) put 16+ concurrent Playwright renders on one box. The Playwright Node driver subprocess died, and then every subsequent scrape returned null forever, until a manual restart. No exception, no alert, no recovery. The fix was three PRs: semaphore + driver-death detection + auto-restart (~2.3s), then the browser pool and pacer, then the same protections for watchlist refresh.

04 · Extraction

JSON-LD, and the three-tier cascade behind it

You asked specifically how JSON-LD parses each platform. The honest answer: JSON-LD is the preferred path, not the universal one — nine platforms needed five different extraction strategies.

What JSON-LD is and why it was the first thing to try

Retail sites embed <script type="application/ld+json"> blocks containing schema.org Product objects — price, currency, condition, availability, image — because that is what Google reads to build rich results. Those sites are incentivized to keep it accurate and present. That makes it the most stable scraping surface on the page: it survives CSS redesigns, which class-name selectors do not.

<script type="application/ld+json">
{ "@type": "Product",
  "name": "Carhartt WIP Detroit Jacket",
  "offers": { "@type": "Offer",
              "price": "185.00",
              "priceCurrency": "USD",
              "itemCondition": "https://schema.org/UsedCondition",
              "availability": "https://schema.org/InStock" },
  "image": { "@type": "ImageObject", "contentUrl": "https://..." } }
</script>

The three-tier cascade (per-listing path)

  1. Tier 1 — structured extractor  $0A hand-written per-platform parser reading the page's own structured data: JSON-LD for Grailed / Depop / eBay / Vestiaire, __NEXT_DATA__.serverState for Mercari, a regex over the escaped RSC payload for Vinted, og: tags plus a DOM price for Poshmark, a data-testid for StockX. Deterministic. All 9 platforms ended up here.
  2. Tier 2 — LLM fallback  ~$0.001/listinggpt-4o-mini via litellm, but only after scoping the markdown to target_elements so “More from seller” and “Similar items” rails are dropped first. Platform-specific prompts (“StockX: Lowest Ask, not Last Sale”). Fires only on fetch failure now.
  3. Tier 3 — stubTitle only, price null. Never silently invents a number.
Why the cascade exists at all

Version one sent the whole rendered page to the LLM as markdown. With 5–10 prices visible on a typical listing page — shipping, related items, Last Sale, seller's other listings — it reliably picked the wrong one. A $45 Depop listing came back as $39.55; Mercari was off by 2–3×; StockX hallucinated prices for items with no asks. ~30% of prices were wrong. Structured extraction took that to ~99% correct at zero marginal cost. The diagnostic that unlocked it was a debug_probe.py that dumped raw HTML, JSON-LD, og: tags and __NEXT_DATA__ for any URL — build that before writing any extractor.

The durable ranking

JSON-LD > framework state (__NEXT_DATA__, RSC payload) > data-testid > og: meta > CSS class names. Class names rotate — Depop's CSS-Module hashes changed and a “block” turned out to just be a stale selector; a follow-up audit found the identical bug sitting on Vinted. Anything you select by class name needs a scheduled re-audit, which is why the full-extractor sweep existed.

05 · Relevance

Stopwords, anchors, and a filter that could not be fixed

Platform search returns whatever it wants. Post-filtering in lib/parse.ts is what made results feel precise — and it is the subsystem that generated the most bugs, by a wide margin.

The chain, in order

  1. Drop sold listings
  2. Title relevance (below)
  3. Size filter — structured size field first, title regex as fallback
  4. Color filter — narrow, essentially just “white” vs “off-white”
  5. Map to Listing, sort by price ascending

Tokenize → stopword → anchor

Lowercase, strip punctuation, split. Keep tokens of 3+ chars plus any pure-numeric token of any length (model numbers: “1”, “4”, “350”). Then drop RELEVANCE_STOPWORDS: articles, colors, sizes, conditions, and — the non-obvious one — every garment-type word. On a fashion resale site, “hoodie” and “jacket” distinguish nothing.

What survives is split into anchors and soft tokens by a frequency test: isAnchor(t) = BRAND_ANCHOR_OVERRIDES.has(t) || !COMMON_WORDS.has(t), where COMMON_WORDS is an English frequency corpus. Every anchor must appear in the title. That AND-logic is what stops a “messi jersey” search from returning a Ronaldo jersey just because both titles say “soccer jersey”. If a query has no anchors at all, fall back to match-any so you never return zero.

The limit you found — and correctly refused to paper over

A query reducing to exactly one surviving common-word token is mathematically unfixable by the override list. For a single-token anchor set, anchors.every(satisfied) and the no-anchor fallback queryText.some(inTitle) reduce to the identical check — “does the title contain this word” — so marking it an anchor changes nothing. Proved with columbia jacket: “Columbia University varsity jacket” matches before and after adding 'columbia'. You left it out of the override set deliberately, because including it would advertise a fix that does not exist. That is entity disambiguation, and it needs a different mechanism entirely.

Design smell, in hindsight

This whole subsystem is a hand-tuned heuristic pile that grew one incident at a time, and it is the part of the codebase with the most documented pitfalls. Next time: a brand entity table (canonical id, surface forms, category) as a first-class data structure, with the token heuristic as a fallback for the unknown tail — rather than a frequency corpus plus an ever-growing exception list.

06 · Caching

Six layers, each solving a different problem

You remembered “caching for frequently used queries.” There were six distinct caches, at three different lifetimes, and conflating them is how cache bugs happen.

Three rules baked in, all learned the hard way

  • Normalize the key, send the query verbatim. Tokens are lowercased and sorted for hashing, so “nike hoodie white” and “white nike hoodie” share a row — but the platform gets the original string.
  • Never cache an empty result. A transient zero-result run would otherwise be pinned for the whole TTL.
  • Adding a field to a payload does not update rows already cached. Every schema change to a cached shape needs a key bump or a purge, or paying users see stale objects missing the new field.
07 · Data layer

Supabase: what RLS does, and the three things it does not

20 public tables by the end. Auth, Postgres, storage and realtime in one service was the right call at this size. The security model had three separate failure modes, each found the hard way.

Shape

auth.users  (Supabase-managed)
     │  ON INSERT → trigger handle_new_user() [SECURITY DEFINER]
     ▼
public.profiles ─┬─ saves ────── collection_folders
                 ├─ watchlist         (price_at_add never changes,
                 ├─ saved_searches     price_current updated on refresh)
                 ├─ search_history
                 └─ notifications ─── alert_matches
Failure 1 — RLS is not a grant

A correct RLS policy still returns Postgres 42501 permission denied without an explicit GRANT SELECT, INSERT, UPDATE, DELETE ON public.<table> TO authenticated, service_role. This bit four tables. On watchlist it presented as “tracked count always shows 0” because the failing count fell back to ?? 0 — a silent wrong number, not a crash. Every new table needs both, and an audit query over information_schema.role_table_grants after you add one.

Failure 2 — RLS scopes rows, never columns

A self-service UPDATE policy on profiles (“users may edit their own row”) let a user set their own subscription_tier. A privilege-escalation hole that breaks nothing and therefore survives every “is anything erroring” audit. Fix: column-level grants. Consequence to remember: a new column then arrives with no grant at all and silently fails to write.

Failure 3 — supabase-js never throws

.insert() and .update() return { data, error }. They do not reject. An unchecked call fails silently, forever, and looks like a product bug months later. Check error on every single write.

Also worth carrying

  • The natural key is the URL, not the scraped id. Listing ids were nanoid-generated per response — ephemeral. UNIQUE (user_id, listing_url) is what makes save/unsave toggling and dedup work.
  • Snapshot vs live is a deliberate split. saves freezes title/price/image at save time; watchlist keeps price_at_add immutable and updates price_current. A refresh failure bumps last_checked_at only and leaves price alone — never overwrite good data with a failed read.
  • Realtime needs the table added to the publication, and channel names must be unique per subscriber or subscriptions silently collide.
  • search_history row counts are not search counts. Know what each table actually measures before quoting it.
08 · Payments

Stripe: checkout, webhooks, and the debt-proof overage

Four routes under /api/billing (checkout, credits, portal, status) plus one webhook. The design goal throughout: never deliver a search you have not been paid for, and never let a retry double-grant.

The flow

  1. Customer resolutionresolveStripeCustomerId() reads the cached stripe_customer_id off profiles, verifies it against Stripe, and on a resource_missing error mints a fresh one and overwrites. This exists because a cached live-mode ID hit with a test-mode key is otherwise a hard crash — a real hazard when you swap keys between local and prod.
  2. CheckoutStripe-hosted Checkout, mode=subscription for plans and mode=payment for credit packs. Price IDs come from env; code never creates a price. supabase_user_id rides in customer metadata, which is what lets the webhook map an event back to a user.
  3. Webhook/api/webhooks/stripe, signature-verified with STRIPE_WEBHOOK_SECRET. Six events handled: checkout.session.completed, customer.subscription.{created,updated,deleted}, invoice.payment_{succeeded,failed}.
  4. Entitlement writetierFromPriceId() maps the price ID to a tier and writes it to profiles. On an unknown price ID it logs loudly and returns free — the loud log is the point, because the silent version downgrades a paying customer when an env var is missing.
  5. PortalStripe Billing Portal for cancels, card updates and invoices. Zero UI to build or maintain.

Webhook idempotency — the pattern to reuse verbatim

Stripe delivers at-least-once. Granting search credits is a non-idempotent read-modify-write, so a re-delivery would double-grant. The guard is a claim-with-rollback against a stripe_webhook_events table:

INSERT event_id INTO stripe_webhook_events   ← claim before processing
  ├─ error 23505 (unique violation) → already processed, return 200, skip
  ├─ other error                    → log, process anyway (fail open)
  └─ ok                             → process
         └─ handler throws → DELETE the claim so Stripe's retry re-runs it

The rollback on failure is what separates this from a naive dedup table — without it, a transient error permanently burns the event and the customer never gets what they paid for.

Credit packs: cash before consumption

Once a tier's included searches are spent, further searches draw down prepaid credits — 100 / 300 / 1,000 searches at $10 / $25 / $60, bought as a one-time Checkout. Marginal cost is ~$0.006/search, so every pack sits well above worst-case COGS. This is the right shape: an unlimited plan with no backstop is an open-ended liability, and metered post-paid billing is a collections problem. Prepaid is neither.

Things that cost you time

Stripe webhooks never reach localhost. Credits “never granted in dev” was not a bug — the code was always correct, Stripe simply cannot POST to your laptop without stripe listen. Separately: test and live are entirely separate universes — separate keys, separate products, separate prices, separate webhook endpoint and secret. Going live is a four-step swap (keys, endpoint, secret, rebuild), not a toggle.

The pricing finding that actually mattered

Every real paying customer signed up, searched, created an alert and paid on day zero — some after only 2 searches against a 5/week free cap. Conversion here was a first-impression impulse buy and had nothing to do with hitting a quota wall. A proposed weekly-pricing change (a ~5× effective price increase) was killed on that number alone, before any code was written. Pull the funnel data before you touch pricing.

09 · Email

Resend, the alert engine, and a channel that was dark the whole time

Alerts were the flagship feature. The email that delivers them is also the project's sharpest lesson about measuring what you build.

Two separate Resend wirings

  • Transactional, from your app. RESEND_API_KEY in .env, called by alertRunner.ts, HTML built by lib/email/alertEmailTemplate.ts (inline styles, table layout, escaped everything — email clients are 2004).
  • Auth emails, from Supabase. Confirmation and password-reset go through Supabase's own SMTP config, pointed at Resend in the Supabase dashboard. Different wiring, different throttles — auth-email rate limiting turned out to be two Supabase limits, not a Resend one, which took real investigation to establish.

DNS is the actual setup

The API key is trivial. What makes mail arrive is three DNS records in Cloudflare: SPF (who may send as you), DKIM (cryptographic signature), DMARC (what receivers should do when the first two fail). You configured SPF and DKIM. _dmarc.thecrawli.com returns nothing to this day.

The alert engine

crontab */15 * * * *  →  /api/cron/run-alerts  (Bearer CRON_SECRET)
      ↓ pick saved_searches WHERE next_run_at <= now  (≤20 per tick)
      ↓ runSearchJob()  ← through withListingsCache: N watchers, 1 scrape
      ↓ applyCriteria()   AND-only: size AND minPrice AND maxPrice
      ↓ diff vs last_seen_urls  →  genuinely new listings only
      ↓ Resend email + notifications row + alert_matches rows
      ↓ next_run_at = nextAnchoredRunAt(cadence_hours)

There is no Vercel Cron. The app is systemd-hosted, so that one crontab line is the recurrence. When it was missing, every saved search's next_run_at froze in the past and alerts went silent with no error anywhere — a whole feature dead, invisibly.

The finding to take into the next project

254 alert emails. 252 delivered. 0 opens. 0 clicks. Meanwhile “the alert email is the strongest driver of a second session” sat in docs/HANDOFF.md for months as a strategic assumption with zero measurement behind it. The first time anyone checked, it found nothing supporting it.

And the calibration matters as much as the number: 254 emails is not 254 trials — they went to a small handful of people. Resend's window silently clamped to ~30 days, so whether this was a regression is unknowable. And no ESP can measure inbox placement: “delivered” means a server accepted the message, never that a human could find it. The correct next step was a falsification test (trigger a real alert, open it, click it, see if Resend registers), not a strategy rewrite. Any feature whose value depends on an email arriving needs an engagement metric checked once before you build strategy on it.

for contrast  Across the last 30 days all Resend traffic combined shows 405 sent · 403 delivered · 23.4% open · 7.5% click. So the pipe works. Something specific to the alert cohort or its placement did not.

10 · Hosting

One Hetzner box, systemd, nginx, crontab

No Vercel, no Docker, no Kubernetes, no CI. A single 8 GB VPS at 5.78.187.97, a git clone in /opt/crawli, and four cron lines. It has been up 60 days.

The stack on the box

Cloudflare
Proxying (orange cloud), TLS termination at the edge, DNS, Turnstile. Full (strict) to the origin.
nginx
Reverse proxy :80/:443 → :3000. Own Certbot/Let's Encrypt cert for the Cloudflare→origin hop. A dedicated www server block 301s to bare for canonicalization.
systemd
Two units: crawli-next and crawli-sidecar. Restart policy is what makes the auto-heal cron work. journalctl -u <unit> -f is the whole logging story.
Deploy
git pull && npm install && npm run build && systemctl restart crawli-next. Manual, over SSH. Order matters — restarting before the build finishes loads old code.
n8n
Same box, global npm install, SQLite at /root/.n8n/database.sqlite, exposed at n8n.thecrawli.com.

The best debugging story in the project

The sidecar was getting SIGKILL'd almost daily around 06:15 UTC. Not OOM — a systemctl restart timeout. Root cause: the 6am compare-refresh cron fanned 33 items × 9 platforms = 297 renders through the sidecar's small render semaphore, monopolized it for 20+ minutes, and starved the */15 smoke test — which then auto-restarted the sidecar mid-batch. The health check was killing the thing it was protecting.

Two fixes, and the second is the interesting one. (1) A heartbeat file at /run/crawli-compare-refresh.heartbeat, touched per slug; the smoke cron skips the restart if it is <10 minutes old, and logs the skip rather than dropping it silently. (2) Rather than tolerate the load, you pulled 30 days of GSC data on the feature — it was earning ~5 clicks a month — and cut the job to 15 curated slugs, weekly. 297 renders/day → 135/week, a 94% cut. The right fix for an expensive job is often deleting most of it, and the usage data is what gives you permission.

Still open on this box

nginx's 300s proxy_read_timeout cuts the client connection on /api/compare/refresh before it finishes, so crawli-compare.log logged nothing from June to September even though the job succeeded server-side every single time. A log that is silently empty is worse than no log — you trust it.

11 · Monitoring

Sentry, UptimeRobot, and the gap between them

Two tools with a clean division of labor — and one whole class of failure that neither catches, which is the part worth remembering.

FailureUptimeRobotSentrySmoke cron

Sentry

Wizard-installed; four files do the work. instrumentation-client.ts (browser — and there must be only one client entry point), sentry.server.config.ts, sentry.edge.config.ts, and instrumentation.ts which dispatches on NEXT_RUNTIME. Wrapped via withSentryConfig() in next.config.ts, which is also what uploads source maps at build time using SENTRY_AUTH_TOKEN — without that, production stack traces are minified garbage.

Two configuration choices that earned their keep:

  • tunnelRoute: "/monitoring" — browser errors route through your own domain instead of directly to Sentry's ingest host, so ad blockers don't silently swallow them. Without it your client error rate looks great and is fiction.
  • ignoreErrors with a written justification per entry. Instagram's in-app-browser bridge (window.webkit.messageHandlers) and mobile Safari's NotFoundError: The object can not be found here. are browser noise, not your bugs. Each was investigated and the reasoning left in a comment before being silenced — that comment is what stops a future session from re-litigating it.

Sampling: tracesSampleRate 0.1 in prod, 1 in dev. Also caught a real one — a fire-and-forget fetch() in a client component reports as an unhandled production error.

UptimeRobot

Two HTTP monitors, both carrying ?token=<INTERNAL_API_TOKEN>:

MonitorEndpointIntervalTimeoutAsserts
Crawli Health/api/health5 min30sNext.js up, sidecar reachable, pool alive
Crawli Smoke/api/smoke15 min60sA real Grailed search returns ≥1 listing, else 503
Why /api/smoke exists — the failure mode with no signal

The Chromium pool got poisoned: sidecar process alive, health check passing green, no exception thrown, and every search returning {}. Uptime said 100%. Sentry said zero errors. The product was completely broken. Nothing that checks liveness can catch a system that is alive and wrong.

The answer is a smoke test that exercises the actual business transaction and asserts on the result, not the status code. And because it returns 503 on failure, the cron can || straight into systemctl restart crawli-sidecar — self-healing for the common case, with no human in the loop. Build the smoke endpoint on day one of the next project.

n8n gotchas you paid for

  • The OpenAI node's output is output[0].content[0].text, not message.content. Guessing an output path is the single most common n8n bug.
  • import:workflow always deactivates the workflow. Re-activate after, every time.
  • Activation and schedule changes only take effect after systemctl restart n8n.
  • The “Available in MCP” toggle is a backend bug in 2.8.4 — it returns 200, echoes your value back, and reverts to false on reload. The only reliable fix is writing the flag straight into the SQLite settings column, last, after all other edits, then restarting.
  • The GSC OAuth refresh token is a separate credential from your user login and expires independently. When it does, the workflow fails at “Refresh Google token” with invalid_grant and there is a documented OAuth Playground procedure to regenerate it.
  • The weekly SEO email undercounts GSC totals by ~5×. Do not plan from a number a workflow computed unless you have reconciled it against the source.

Also built: a PRAW sidecar (reddit-service/, FastAPI on :8100) as a drop-in replacement for Zernio's Reddit search, response-shape-compatible so no n8n node had to change. Official API, 100 queries/min, full listing access. Good migration discipline.

13 · Distribution

116 blog posts, 33 compare pages, and a settled experiment

You said you'd cover marketing. This is the engineering-and-SEO half: what was built, what it was measured on, and the standing instruction that came out of it.

What exists

  • 116 markdown posts in content/blog/, parsed at build time by lib/blog.ts with gray-matter + marked. Frontmatter carries faq[] (mirrored into FAQPage JSON-LD, question and answer matching visible text exactly, because Google requires that) and compareSlug, which links a post to its live-price page.
  • 33 /compare/[slug] pages generated from a Supabase table, with Product + AggregateOffer schema and real prices refreshed by cron. ISR at revalidate=3600.
  • The technical SEO surface: sitemap.ts with real lastmod dates (post updated, snapshot scraped_at, or last git commit — never new Date(), which destroys the freshness signal), robots.ts, RSS at /feed.xml, opengraph-image.tsx, a PWA manifest, SoftwareApplication + SearchAction JSON-LD, llms.txt, and security headers in next.config.ts.
  • Two indexing channels: IndexNow (Bing/Yandex/Naver, best-effort, never throws, fired on deploy and by the compare cron) and the Bing Webmaster Submission API via scripts/submit-bing.mjs, which requests an actual priority recrawl. You needed the second because IndexNow alone leaves a young domain sitting in “Discovered — currently not crawled.”

What it returned

3 months (Jun 29 – Sep 28): 26.6K impressions → 224 clicks → 0.8% CTR, average position 10.5.

Position has improved steadily (24.3 → 7.7 over the window) and impressions have quadrupled. Clicks have not followed. About half of all clicks were brand search: in a mid-September 90-day pull, the homepage alone carried 87 of 176 clicks at 7.37% CTR, and all 116 posts together produced the other 89. The worst single case: best-secondhand-marketplaces-for-luxury-items at 4,894 impressions, 7 clicks, 0.14% CTR.

The standing instruction you wrote, and should keep

“Stop writing blog posts.” 116 posts producing ~39 clicks in 90 days, with compare pages at zero clicks from 696 impressions at position 9, is a settled experiment. The AI Overview owns these SERPs; a full rewrite did not dislodge it. Ranking on page one and getting no clicks is not an optimization problem, it is a channel that has changed shape.

Two corollaries you found: a blog post and its compareSlug page cannibalize each other for the same query; and a large share of remaining impressions are synthetic AI-tool queries, which structurally deflates CTR and means the metric itself is partly fiction. Compare pages were reclassified as an AI-answer-engine surface to be kept fresh, not a click source — and explicitly stopped being measured on clicks.

Two more findings worth carrying

  • “crawli app” had literally zero impressions for 90 days — not ranking low, never appearing. Cause: the word “app” appeared nowhere in crawlable copy. The site had SoftwareApplication schema and a PWA manifest, and neither mattered. Schema and manifests carry far less term-matching weight than visible title, meta and H1 text. If you want to rank for a word, put the word on the page.
  • Five public files duplicated the pricing matrix with nothing keeping them in sync, and all five drifted past a repackaging — one asserting a feature was free that the paywall had just made paid. These are exactly the files AI answer engines read to tell a prospect what you cost. A stale number there gets quoted back as fact.
Read the next section before acting on this one

Everything above is measured in clicks, which was the only number anyone was looking at. Bing's AI Performance tab tells a materially different story about whether this content was being consumed — §14.

The part that was right

The call to treat compare pages as “an AI-answer-engine surface, not a click source” and to stop measuring them on clicks was made on instinct, before this data existed. It was correct. 6,189 citations at an average of 9 distinct pages per day is a corpus being actively mined — the structured data, the FAQ schema, the Product+AggregateOffer markup and the real refreshed prices did exactly the job they were built for. That work was not wasted; it was being consumed through a door nobody was watching.

The part that does not follow

A citation is not a visit, not a signup, and not a dollar. These 6,189 citations coincide with the flattest stretch of the funnel in the project's life. Copilot quoting your price table answers the user's question inside Copilot — that is the AI Overview dynamic from §13, seen from the supply side rather than the demand side. So this does not reopen “write more blog posts”; if anything it explains why the clicks never came. It reframes the asset from “failed traffic channel” to “successful citation channel with no conversion path attached,” and the missing piece was never more content. It was a reason for someone reading a cited answer to come to the site — something only the live product could offer, and nothing in the cited pages ever asked them to.

Three things to check before trusting any of this

  • The gaps are suspicious. Jul 27–Aug 6 and Aug 21–23 drop to near zero and then snap straight back to 149 and 230. Real demand does not do that. Those are far more likely reporting gaps or crawl pauses on Microsoft's side than genuine collapses — which means the true total is probably higher than 6,189.
  • “Citation” is Microsoft's definition, not yours. It counts an appearance in a generated answer. It does not distinguish a load-bearing citation from a footnote in a list of eight, and there is no public methodology to audit.
  • This is Bing and Copilot only. ChatGPT, Perplexity, Claude and Google's own AI Overviews are all invisible here. The real cross-engine citation number is unknown and unknowable from this dashboard — 6,189 is a floor on one surface, not a total.
Carry this forward

You had a geo-optimizer MCP wired up for exactly this and the GSC/GA4 dashboards checked regularly — but the Bing AI Performance tab went unexamined for three months while it accumulated the single most interesting number in the project. The lesson is the same one as the alert emails in §09, in a different costume: you were not short on instrumentation, you were short on the habit of looking at it. Next project: one weekly review that reads every dashboard you have, including the ones you do not expect anything from.

16 · Carry forward

What to repeat, and what not to

Repeat

keep
Diagnose before you build

debug_probe.py before any extractor. engine_bakeoff.py (72 URLs × 2 engines) before switching scrapers. bench-sidecar-concurrency.py before tuning a limit. Every one of these prevented a large wrong decision.

keep
A smoke test that asserts on the transaction

Liveness checks cannot catch a system that is alive and wrong. One endpoint that runs a real search and asserts length > 0 caught the worst outage class you had — and self-healed it.

keep
Deferred work as specs with trigger conditions

C1–C4 each had a written trigger (“when p95 > 30s”, “when success rate < 70%”). You knew exactly when to act and never built any of them prematurely. Far better than a TODO list.

keep
A pitfalls file with why, not just what

The entries that saved the most time are the ones recording what was tried and rejected, and what a mechanism provably cannot do. That is the knowledge that otherwise dies with a session.

keep
Claim ledgers and pre-registered kill criteria

“Marketing copy may only use a claim at Validated” and “write the hypothesis and kill criterion before shipping, not after reading the result” are both unusually disciplined for a solo project. They killed at least two bad decisions.

keep
Prepaid credits over post-paid metering

Cash before consumption. No collections, no open-ended liability, no surprise invoice. And webhook idempotency via claim-with-rollback.

Change

change
Instrument the funnel on day one

GA4 has no key events configured. Alert emails ran for months with nobody checking a single open. Retention was never measured until a September audit. You cannot fix a second-session problem you have not looked at — and every metric you did eventually pull changed a decision.

change
Test the constraint before architecting around it

eBay sat on a 60-second, 6-result, credit-burning path for months because of an untested belief. Keep an explicit list of load-bearing assumptions and mark which are measured.

change
Distribution before more surface area

116 posts, 33 compare pages, 55 TikToks — and the homepage's brand traffic still carries half the clicks. Nine well-parsed platforms, sold comps, alerts, flip margin and onboarding all shipped while the second-session problem went untouched.

change
Read every dashboard you own, weekly

6,189 Copilot citations accrued over three months in a Bing tab nobody opened, while alert-email engagement sat at zero in a Resend tab nobody opened. Both were instrumented. Neither was looked at. The gap was never tooling — it was the absence of a standing review.

reframe
Optimize for the citation, then for the click

Structured data, FAQ schema and real refreshed prices made the site genuinely citable — that part worked and would work again. What never existed was a reason for someone reading a cited answer to leave it and come to you. Build the hook into the cited page, not just the ranking.

change
Secrets hygiene from commit one

A service_role key across 7 committed files — caught and rotated same-session, the legacy key disabled a week later, and every copy scrubbed from history before publishing. Pre-commit secret scanning would have caught it before the first commit, which is ten minutes of setup.

change
Entity data, not heuristic piles

Relevance filtering grew one incident at a time into a frequency corpus plus a 40-entry exception list with a provable dead end in it. Model brands as data from the start.

change
One list, not four

The platform set lived in four places (Python, TypeScript, schema, homepage component) and the pricing matrix in five public files, none kept in sync by anything but vigilance. Generate them, or test that they match.

The one-line version

The engineering was strong and got stronger — 21× cheaper, 8× faster, self-healing, nine platforms parsed accurately. The content was strong enough that an answer engine quoted it 6,189 times. The weak leg was never building or writing; it was looking — and the two things nobody looked at (did the alert email arrive, did anyone come back a second time) are exactly the two that decided the outcome. Next project: build the retention instrument before the ninth feature, and put a standing weekly read on every dashboard you own.

**2026-08-29: Trading cards were passing player/celebrity-name searches under a category filter**
`titleMatchesQuery`'s anchor check verifies WHO a listing is about, not WHAT it physically is, so a "jeff teague jersey" search (single real anchor: `teague`) matched that player's trading cards too. Compounded by `filtersToQuerySuffix` appending the bare category word ("tops") onto the marketplace query text, which fuzzy-matched the "Topps" card brand and "Top Flight" streetwear brand — a category filter was actively pulling in *more* junk. Fixed with a title-text exclusion list (`NON_APPAREL_SIGNAL_WORDS` in `lib/parse.ts`), gated on a category filter being active (owner decision — unfiltered searches untouched) and skipped when the query itself asks for a card. Verified against 8 cases (signed jerseys, Chrome Hearts, Relic by Levi's, explicit card searches all still pass); `npx tsc --noEmit` clean, existing `verify-relevance-numerics.mts`/`verify-alert-query.mts` still 100%. See PITFALLS "Relevance filtering".

**2026-08-29: Sidecar OOM incidents — reduced concurrent Chromium from 6 to 2, added daily memory monitoring**
Three 503 Service Unavailable incidents in 24 hours (2026-08-28 to 2026-08-29) revealed `SIDECAR_MAX_CONCURRENT_RENDERS=6` (default) allowed too many concurrent Chromium processes, exhausting 7.6GB RAM and triggering OOM kills. Fixed by reducing to 2 via systemd drop-in `/etc/systemd/system/crawli-sidecar.service.d/override.conf` — memory immediately dropped from 7.5Gi to 4.4Gi, incidents ceased. Added daily monitoring script `/opt/crawli/monitor-memory-trend.sh` (logs to `/var/log/crawli-health-trend.log`, runs 09:00 UTC daily) to detect future memory leaks. Documented monitoring approach and two higher-fidelity alternatives (sidecar profiling, full observability) in [`docs/reference/MEMORY_LEAK_MONITORING.md`](docs/reference/MEMORY_LEAK_MONITORING.md). See that doc for incident details and escalation paths if memory creeps again.

**2026-08-26/27: Photo search, identify item(s) from a photo, auto-fills the search box or offers a pick**
New "Photo search" button (visible text label, not icon-only, since hover titles don't work on mobile, the feature's primary use case) in `SearchForm.tsx` sends a client-resized (max 1024px, JPEG) photo to a new sidecar endpoint `POST /identify-photo` (`crawl4ai-service/main.py`, `resolve_llm()`/litellm pattern shared with `/expand-query`, currently `openai/gpt-4o-mini`, no new provider key). The endpoint returns `{"items": [...]}`, up to 4 distinct clothing/accessory items found in the photo. A single item auto-fills the query directly; multiple items (e.g. a full outfit) render as tappable chips instead of guessing which one the user meant, tapping one fills the query. Always auto-fill/pick only, never auto-runs the search, field stays editable. Proxied via `app/api/search/identify-photo/route.ts` following `lib/scraper.ts`'s existing sidecar-call shape. Reverse-image-match-against-live-listings was considered and explicitly rejected (it's Gem's core differentiator; see `docs/superpowers/specs/2026-08-26-photo-search-design.md`). Prompt asks for real specificity now (material, pattern, notable model/product name if legible) and reads visible printed text/logos rather than treating them as a risky guess to avoid, that distinction is what fixed an earlier bug where a legible "SUPREME" wordmark got dropped in favor of a generic description. **Found and fixed during build:** `litellm.acompletion()`'s `timeout=` kwarg let a malformed-image request hang ~15 minutes instead of failing in 15s, same class of bug as `/expand-query` (see PITFALLS.md), fixed with `asyncio.wait_for()` since this endpoint isn't fire-and-forget like that one. **Open finding from the specificity experiment:** the stricter multi-item JSON prompt is measurably more conservative than the original single-string version, a low-quality/ambiguous test image that previously always got a best-effort guess now correctly returns zero items instead. Reasonable behavior (the toast fallback reads fine), but worth watching on real photos: a "couldn't identify" failure has a real UX cost if it fires more often than expected. Verified: `npx tsc --noEmit` clean, sidecar tested directly (single-item, multi-item, timeout, malformed-input, empty-result paths). **2026-08-27, UI redesign:** the original layout (3 buttons cramped in one row, full stack on mobile) tested as messy. Brainstormed via the visual companion + `ui-ux-pro-max`/`frontend-design` skills; kept the same input/photo-button/search-button shape but fixed hierarchy: Photo search is now ghost-styled (transparent until hover) so it visually recedes behind the gradient Search CTA instead of competing with it, the loading state gets an accent-tinted background instead of just graying out, and the multi-item picker is wrapped in its own bordered panel with a tight "Found in your photo" caption instead of loose pills. Mobile goes from 3 stacked full-width rows to 2 (input alone, then Photo + Search paired via a `sm:contents` wrapper that dissolves into the desktop row at the `sm` breakpoint), and the label shortens to "Photo" at that width. Verified with a real browser render (Playwright against a standalone Tailwind test page mirroring the exact classes, not the live app, since `/search` is auth-gated and no test session was available) at 375px and 900px: mobile correctly shows 2 rows, desktop correctly shows the original single row. **Not yet verified in the live app with a real photo.**

**2026-08-25: eBay moved from Avenue B to a native search-grid extractor — 60s/6 results → ~7s/75 results**
eBay was the last platform on the Firecrawl discover-then-scrape-each-listing path: one `site:` search plus 10 per-listing Chromium renders at concurrency 2, i.e. 5 sequential rounds. Benchmarked before the change (`scripts/bench-platform-latency.mts`, 3 queries, isolated): **median 60.2s and 6 listings, against 5.6-12.2s and 10-98 listings for the eight native platforms** — slowest by 5x and least productive, while also holding 2 of the sidecar's 6 render slots for 42s and slowing every other platform in the same search. End-to-end that was 67.0s with eBay vs 27.3s without. It turned out eBay never needed Avenue B: its own SRP (`/sch/i.html?_nkw=`) is **server-rendered** and yields ~81 cards with title, price, image, size and condition in one ~5s request. New `extract_ebay_grid` in `search_page_extractors.py` (+ `ebay` in `NATIVE_PLATFORMS`, `SEARCH_PAGE_PLATFORMS` both sides, and `FIRECRAWL_FALLBACK_PLATFORMS`). Now ~7-11s for 65-80 listings, and the full 9-platform fan-out returns **350 listings in 42.8s** where it used to return 122 in 67.0s. **Verified on prod's own IP without deploying** (read-only probe, since the datacenter IP is the thing Akamai actually walls): 5/5 spaced then **8/8 concurrent**, 65-82 listings each, ~4.4s, zero interstitials. Two traps are documented in PITFALLS and must not be undone: eBay's search render **must not** have a `wait_for` (it can't help on server-rendered HTML and turns a 3s block into a ~100s one — this was measured, and it briefly made a 9-platform search *slower* than the path it replaced), and the SRP's classes are `su-card-container`/`s-card__*`, not the `s-item__*` family every older eBay scraper uses. `ALERT_EXCLUDED_PLATFORMS` still excludes eBay — its stated rationale is now obsolete and the comment says so, but letting eBay into alerts raises recurring cron load, which is a product call. **Not yet deployed, and not yet verified in a browser.**

**2026-08-25: ThredUp returned 0 results for any model-number query — three separate bugs**
`levis 501 jeans` fetched 100 ThredUp rows and kept **none** of them. (1) `titleMatchesQuery` rule 1 tested the query's model number against *any* number in the title, but ThredUp synthesizes titles from structured attributes so the only number present is the garment size — and `100% Cotton` supplied a bogus `100`. `nonModelNumerics()` in `lib/parse.ts` now strips size and percentage contexts first, and rule 1 abstains when nothing is left rather than rejecting; text anchors still apply, so the RE/DONE and Weekday jeans ThredUp mixes into a Levi's grid are still correctly dropped. (2) `extract_thredup_grid` never unescaped `brand.name`, so `"Levi&apos;s"` never matched `"Levi's ..."` and got prepended to a title that already had the brand — **85 of 100 rows** rendered as `"Levi&apos;s Levi's Blue Jeans Size 36 waist"`, entity visible in the UI. (3) Independently, a shopper's collapsed spelling could never match a possessive brand on **any** platform, because `Levi's` tokenizes to `levi` + a dropped `s`; fixed with a token-level rule in `anchorSatisfied`. Result on the original query: **100 rows in, 85 kept, 0 wrong-brand survivors, 0 Levi's rows wrongly dropped.** A/B on identical live rows across all 9 platforms showed every delta between **0 and +6, never negative**, and no-numeric queries bit-identical. New `scripts/verify-relevance-numerics.mts` (23 checks).

**Audited whether the ThredUp defects applied to the other 8 platforms — two did, and one was much wider than ThredUp.** (a) The **entity/duplicated-brand** bug is ThredUp-only: zero occurrences anywhere else across 3 entity-prone brand queries, because bs4 decodes entities in `get_text()` and attributes, so it can only survive where JSON is parsed out of a `<script>` tag. (b) The **possessive-brand** bug was never ThredUp-specific — measured on live rows, `victorias secret bra` matched **0 of 20** "Victoria's Secret" titles, `chicos jacket` **6 of 99**, `dillards blazer` **0 of 4**; all are 100% after the fix. The per-brand `ALIAS_GROUPS` entry written for Levi's was **removed** in favour of the general rule, which requires the apostrophe so it matches "Victoria's Secret" without swallowing **Victoria Beckham**. (c) Found a third, new one in the same family: **Vestiaire's `str.title()` mangled possessives** into `"Levi'S 501 straight jeans"`, 15 of 15 rows, visible in the results UI — fixed, and now 0. Low keep-rates that looked alarming were checked and are correct: ThredUp kept **19 of 19** real Lands' End rows and dropped all 81 Columbia/Danskin rows. **Separately noted, not fixed: ThredUp intermittently serves a Cloudflare JS challenge** (hit ~3 times during this session, 0 rows each) and, unlike Mercari/Depop/eBay, is **not** in `FIRECRAWL_FALLBACK_PLATFORMS`, so a challenged render is simply 0 results.

**2026-08-22 — Deep-dive brand-anchor audit: 24 more mall/luxury/hypebeast/watch brands fixed, 3 flagged as needing a different mechanism**
Follow-up to the same-day Acne Studios fix, requested explicitly as a broad sweep: checked ~80 well-known brands (Louis Vuitton, Prada, Gucci, Chanel down through Hollister, PacSun, Uniqlo, Arc'teryx, Rolex, Calvin Klein) against `commonWords.json`. Added 24 words to `BRAND_ANCHOR_OVERRIDES` for the ones that weren't: `casio`, `tiffany`, `shock` alone, plus full both-halves pairs for phrases where every word is ordinary English — `chrome`+`hearts`, `fear`+`anti`+`social`+`club`, `stone`+`island`, `under`+`armour`/`armor`, `lee`, `calvin`+`klein`, `american`+`eagle`, `banana`+`republic`, `free`+`people`. Verified with 31 before/after adversarial cases (each "should NOT match" title built to contain *exactly one* of the query's common words, e.g. "Roman Armour costume shirt" against "under armour shirt") — 30/30 fixable cases now correctly exclude the off-brand title; re-ran the earlier acne/omega/ralph-lauren/north-face regression set and the full `compare_items` brand audit, zero regressions, `npx tsc --noEmit` clean. **Found and proved a mechanism-level limit along the way:** a query that reduces to exactly one surviving common-word token (e.g. `"columbia jacket"` → just `{columbia}`) cannot be fixed by any override — `anchors.every(...)` over a single anchor and the no-anchor OR-fallback are mathematically the same check. Left `'columbia'` **out** of the override set rather than add it and imply the collision (Columbia Sportswear vs. Columbia University) is handled. **Three brands flagged as needing a different fix, not a missing override:** Old Navy (`'navy'` is a deliberate color stopword, `'old'` alone is too generic), Off-White (already a documented, deliberate exclusion — conflicts with `colorFilter.ts` treating "off-white" as a color), and J.Crew/H&M (their distinguishing token is a single letter, dropped by `relevanceTokens`' length filter before it ever reaches the anchor stage — needs new tokenization logic, not an override). Full writeup and the audit method for adding a future brand: PITFALLS "Relevance filtering".


**2026-08-22 — Brand queries with no anchor word silently stopped filtering by brand: fixed for Acne Studios + 3 more live cases found by audit**
Root cause: `titleMatchesQuery` (`lib/parse.ts`) requires a query's "anchor" tokens (non-common words, or entries in `BRAND_ANCHOR_OVERRIDES`) to all appear in a listing title; with zero anchors it falls back to "match at least one token." "acne studios long sleeve" had all 4 tokens in the common-English corpus, so anchors was empty and the query matched any brand's long-sleeve item. Fixed by adding `'acne'` to `BRAND_ANCHOR_OVERRIDES`. **Audited all 33 real `compare_items` brands for the same empty-anchor failure** (script computed anchors for each brand's bare, no-model query and flagged empty results) and found it live for 3 more: `"omega watch"`, `"ralph lauren shirt"` (without "polo" in the query), `"north face jacket"` (without "nuptse"). Fixed by adding `'omega'`, and — since Ralph Lauren and North Face are phrases where *both* words are ordinary English on their own — `'ralph'` + `'lauren'` and `'north'` + `'face'` together (anchoring just one word of either still let a same-category listing from a different real brand sharing that word through, e.g. "LC Lauren Conrad" on a lone `'lauren'` anchor). Verified all 4 cases against both a real-brand title (must match) and a same-category different-brand title (must not match), before and after; re-ran the full 33-brand audit post-fix with zero remaining gaps. `npx tsc --noEmit` clean. See PITFALLS "Relevance filtering" for the general rule (one word suffices for a single-distinctive-word brand; all words required for an all-common-words phrase) and how to re-run the audit for a newly added brand.

**2026-08-20 — Alerts: a comma-separated query could never match, 3 of 12 live alerts were dead**

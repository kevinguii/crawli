**2026-08-18 — Sold comps: floor 10 → 5, plus the individual sales behind every median**
Follow-up to the invisibility fix below, driven by the owner's own dead query ("bape baby milo japan tee" returned `available=false` with 5 Grailed and 3 Poshmark sales sitting right there). Measured across 20 real queries pulled from `search_history`: the old floor of 10 produced an aggregate for 14 of them, a floor of 5 for 17, and *any* data at all existed for 18 — so 2 of 20 are genuinely empty and no design reaches them. The fix separates two things that were wrongly sharing one threshold. `MIN_SAMPLE` guards a **claim** ("this sells for $X") and is now 5; it must not go lower, because `trimPriceOutliers()` no-ops below 4 comps and a floor under that publishes an unfenced median. The individual sales are **evidence**, not a claim, so they carry no floor: new `SoldCompsResult.sales` (`PlatformSales[]`) returns dated, priced, linked, newest-first rows per platform, capped at `SALES_ROW_CAP = 50`, built from the comps already fetched — **zero extra requests**, since `statsForPool()` was already returning them and `getSoldComps()` was throwing them away. A thin query now renders rows under a "too few sales to put a median on it" line. Free users get **nothing** new. The paywall appears exactly where there is real data to withhold and nowhere else (owner decision, settled after two rounds — an earlier pass made the lock unconditional with a fabricated no-data backdrop, then reverted): `toLockedResult()` drops `sales` wholesale rather than stripping fields (every column on a row is the product) and its `available` is `platforms.length > 0`, which already folds in thin platforms (a platform with 1+ sales passes through as `n` + `windowDays`, same two non-secret facts a fat one exposes, no median needed). A query with **zero** sales on either platform renders the plain "not enough completed sales" note — identical wording for free and Pro, unblurred, no upgrade prompt — because there is nothing real to sell as premium there. `PriceSummary` mirrors this for the search-results panel: Low/Average/High always paywalls (real listing data, a different source, always present), but the sold-comps sub-block inside it only renders — blurred — when `sold.available` is true; otherwise the same shared `SOLD_NO_DATA_TEXT` note sits below the paywalled card, outside the blur. `fakeSoldStats()` is the only fabrication left; the placeholder generator that invented a fake sample size for empty queries was added and then removed in the same session once this landed. New `SoldSalesList.tsx` (rows interleaved by recency, each attributed to its own marketplace — the no-pooling rule is about *numbers*, not about listing a dated sale). Search results show 5 rows and link to `/price-check?q=`, which now accepts the param and shows up to 50; because that page got long, `SoldCompsLookup` gained a `variant="tabbed"` mode splitting **Recent sales** from **Flip margin** (onboarding's tail keeps the inline layout). `sold_comps_cache` payloads written before this have no `sales` key and are normalized to `[]` on the cache-hit path rather than invalidated. Verified: `verify-paywall.mts` **55/55** (up from 37 — no sale-row field, value, URL, title or date survives stripping; a thin rows-only platform still locks and carries its count; a genuinely empty result does **not** lock; aggregate and rows for one platform collapse to a single locked row using the post-trim `n`), `verify-sold-comps.mts` all passed (new unit checks for no-floor rows, ISO `soldAt`, newest-first ordering, cap vs total), `npx tsc --noEmit` clean, `npm run build` clean, eslint clean on every new file. Live check on the query that started it: 2 aggregates plus rows where there were none.

**2026-08-18 — Alerts joined the "Unlimited" set: Pro's saved-alert cap 8 → 25**
Follow-up to the same-day search/results change, prompted by the owner asking whether alerts were cheap enough to do the same thing to. They are, but not for an identical reason: `nativeResultsCap` is free at any value (a post-fetch `.slice()`) and a search is one-off, but a saved alert is a **permanent recurring job** — every one added re-runs its query daily forever via the crontab in `/api/cron/run-alerts`, so this is cheap-per-unit and linear, not literally free the way the other two are. Grounding measured 2026-08-18: alert runs never touch Firecrawl (`ALERT_EXCLUDED_PLATFORMS` excludes eBay, the only metered platform, from every alert run — crawl4ai compute only, sharing the same cross-user cache live search uses), the cron is a systemd crontab on our own box ticking every 15 min with ≤20/tick capacity (1920/day) against an actual total of **13 alerts across all 48 users**, and the busiest real user ever is **3** (the owner's own Pro account) — nobody has ever approached the old cap of 8. `TIER_CAPS.pro.maxSavedSearches` → 25 (legacy `max` bumped 20 → 30 to keep it above Pro, though no account resolves to it), `/pricing` now reads "Unlimited alerts, checked daily" on Pro, and `/api/saved-searches` POST got the same tier-specific 402 treatment as `/api/search` — a Pro user hitting the cap sees "get in touch, we'll lift it" instead of "upgrade your plan" (Pro *is* the top plan), plus a `[quota] PAID user hit the alerts abuse backstop` server warning. The one live Pro profile was backfilled (`max_saved_searches` 8 → 25) the same way the earlier change backfilled search/results caps. `npx tsc --noEmit` clean, `npm run build` clean, `verify-paywall.mts` 55/55 (its "every profile matches its tier caps" check picked up the backfill), eslint unchanged at baseline.

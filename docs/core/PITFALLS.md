## SEO / indexing

**IndexNow key file must stay in `public/` (added 2026-07-01)**
`public/421d3af41bc04a0439069010586fcb56.txt` is Bing's domain-ownership proof — its name AND contents must equal `INDEXNOW_KEY`. Delete it or change the env without updating both and IndexNow submissions silently 403. Submissions (`lib/indexnow.ts`) are **best-effort and never throw** — a failed ping must not break a deploy or the compare cron, so callers don't need try/catch. Locally you'll see `ok:false` / a 4xx in logs because the API rejects `localhost` URLs; that's expected, it works in prod. IndexNow is Bing/Yandex/Naver only — it does nothing for Google (Google indexing is driven via GSC, not code).

**Sitemap `lastmod` must reflect real dates, not `new Date()` (fixed 2026-07-01)**
`app/sitemap.ts` used to stamp every URL with "now", which makes Bing/Google distrust the freshness signal. It now derives real dates: posts `updated||date`, compare pages `scraped_at` (`getCompareLastUpdated()`), static pages last-git-commit (`lib/gitLastModified.ts`). The git helper shells out to `git log` and only works because prod is a persistent `git pull` clone — it falls back to build time if `.git` is absent. If you add a new static page to the sitemap, give it a `gitLastModified("app/<route>/page.tsx")` entry, not a bare `new Date()`.

**The IndexNow URL list must be derived from the sitemap, never rebuilt by hand (found 2026-08-17)**
Bing Webmaster Tools raised "Some important pages weren't submitted via IndexNow" (1 page). Cause: `app/api/indexnow/submit/route.ts` built its own list of public URLs with a hardcoded `staticPages` array, next to `app/sitemap.ts` which built the same list separately. The two drifted — the sitemap emits the `/compare` hub (priority 0.9) and the IndexNow list didn't, so that page was never pinged. `buildAllUrls()` now calls `sitemap()` and maps `entry.url`, so the two can't diverge again. **If you add a public route, add it to `app/sitemap.ts` only** — IndexNow follows automatically. Importing the sitemap into a route handler is safe: `gitLastModified` is fully try/caught with a build-time fallback.

**IndexNow alone doesn't get URLs crawled promptly on a young domain (found 2026-07-09)**
"Discovered but not crawled" in Bing Webmaster Tools can persist for days/weeks even with IndexNow firing correctly — IndexNow only notifies Bing a URL changed, it doesn't force a recrawl, and Bing gates actual crawling by domain authority. For any real content change (new/edited blog post, new compare item, title/description edit), also run `node scripts/submit-bing.mjs <path...>` — the Bing Webmaster Submission API, which is the same "Request Indexing" action as the WMT UI button. See `docs/reference/SERVER_REFERENCE.md` "Bing priority reindex" for quota details (shared with manual UI submissions, don't resubmit unchanged URLs).

**A blog post and its `compareSlug` page cannibalize each other (found 2026-08-08)**
Every `<item>-resale-price.md` post and its `/compare/<slug>` page targeted the identical head term ("<item> resale price"), and GSC shows Google indexing **exactly one page per pair, almost never both**: of 22 luxury pairs, 8 had only the blog indexed, 3 only the compare page, 1 both, and 10 neither. When adding a new compare item + guide post, the compare page owns `"<item> resale price"` and the post must be titled for a different intent — the "how to vet a cheap listing" angle these posts already contain works well. Don't ship a pair whose two `<title>`s differ only by suffix.

**Whole publish batches get "Discovered — currently not indexed" (found 2026-08-08)**
The 18 luxury compare items added in one day on 2026-07-25 went almost entirely unindexed (16 of 18), while every compare page from the 2026-06-30 batch is indexed. Same template, same word count (~1,950), 200s, correct canonicals, sub-600ms TTFB, all in the sitemap — so **don't go looking for a technical bug**. It's crawl budget plus a large same-day batch of same-shaped pages in a high-competition vertical on a low-authority domain. Ship new compare items and price-guide posts in small batches spread over weeks, and give each one an inbound link from a page that already earns impressions.

**`SearchAction` must point at `/compare/search`, never `/search` (removed 2026-08-08, re-added 2026-08-13)**
`StructuredData.tsx` originally declared a `SearchAction` pointing at `/search?q={search_term_string}`. `/search` is auth-gated and `Disallow`ed in `robots.ts`, so the searchbox could never work, and Google crawled the literal `{search_term_string}` placeholder as a URL (it showed up in GSC "Blocked by robots.txt"). It was removed, then re-added 2026-08-13 targeting the new **public** `/compare/search?q=` page instead. Three constraints hold it together, and breaking any one re-creates the original bug:
1. `/compare/search` must stay publicly fetchable — no auth, no `Disallow`.
2. `robots.ts` no longer carries the blanket `/*?*q=` rule. That rule existed to block raw search queries, but `/search` is already fully disallowed, so it was redundant there while silently blocking the new page. **Don't re-add `/*?*q=`.**
3. `/compare/search` sets `robots: { index: false, follow: true }` in its own metadata. That's what keeps arbitrary `?q=` permutations out of the index without blocking the crawl the SearchAction declaration needs to be verifiable.

**`--surface` is transparent in dark mode — never use it on a floating overlay (found 2026-08-13)**
`app/globals.css` defines `--surface` as `rgba(255, 255, 255, 0.04)` in dark and an opaque `#f4f4f3` in light. That's fine for inline cards sitting on `--bg`, but anything that floats over page content (dropdown, popover, menu, tooltip) becomes see-through in dark mode only. `HeroSearch`'s typeahead shipped with this bug — the hero's value pillars read straight through the results list, and it was invisible in light mode. Use **`--bg-elevated`** for overlays; it's a solid colour in both themes (`#161614` / `#f7f7f6`). Always check a new overlay in dark mode specifically, since light mode will look correct either way.

**`/compare/search` is a sibling route on purpose, not `/compare?q=` (added 2026-08-13)**
Reading `searchParams` inside `app/compare/page.tsx` would opt that page out of its `export const revalidate = 3600` and make the main comparison hub dynamic on every request. A static `search` segment also takes routing precedence over `[slug]`, so it never collides with `/compare/<item>`. If you ever need query params on the hub itself, move the reading into a child component wrapped in `<Suspense>` rather than putting them on the page.

**The weekly n8n SEO keyword email undercounts GSC totals by ~5x — don't plan from it (found 2026-08-17)**
The 2026-08-16 email reported "200 queries, 13 clicks, 1132 impressions" for the trailing 28 days. Pulling the same window from the GSC API directly gives **6,043 impressions and 36 clicks**. The workflow appears to aggregate only the top ~200 query rows, and Crawli's traffic is overwhelmingly long tail, so most of it never reaches the total. Per-query positions in the email *are* accurate; the totals, the CTR, and especially the "not ranking" labels are not — several keywords it flagged as unranked already have posts (`harris-tweed-authentication-guide`, `cavalry-twill-fabric-guide`, `how-to-price-secondhand-clothing`, `fendi-baguette-bag-resale-price`). Acting on those labels would create cannibalizing duplicates. Always re-pull with `mcp__gsc__search_analytics` before committing to a content plan.

**A large share of GSC impressions are synthetic AI-tool queries, which structurally deflates CTR (found 2026-08-17)**
~430 impressions in the 28 days to 2026-08-16 came from persona prompts ("i am in my 40s or older, with a lifetime of established tastes… what is the average resale value of a chanel classic flap bag?") and `after:2026-07-25` operator syntax. They average position 42, are 99% desktop, and have never produced a click. This is what splits the device numbers: mobile sits at position 8.3 / 1.12% CTR against desktop's 18.2 / 0.20%. Two consequences: site-wide CTR reads worse than the human experience actually is, and **an apparent content gap may be entirely synthetic** — the Chanel cluster looks substantial until you notice every query in it is a bot prompt. Check the query text before treating a keyword cluster as demand.

**Never put `min_price_usd`/`max_price_usd` in a compare page's title or description (found 2026-08-17)**
`compare_snapshots` still carries the residual outliers documented in HANDOFF.md "Compare-page floors" — a $29 "Cartier Love Bracelet" and a $73 Depop platform average on the same item (real ones are $3.6k–$6.8k), a $5 "Ralph Lauren Polo Shirt", a $72,530 Grailed ask. A naive `From $${min}` snippet hands exactly those numbers to Google as the item's headline price. `generateMetadata` in `app/compare/[slug]/page.tsx` instead calls `typicalPriceBand()`, which averages **per platform** (absorbing one junk listing), sorts those averages, and drops the cheapest and priciest platform when there are ≥4 (absorbing a wholly junk platform like Depop's fake Cartier inventory). Verified across all 33 items. If you add a new surface that quotes a compare price, reuse that helper rather than the raw columns — and say "asking price", since these are live listings, not sold comps.

**Compare page counts must come from platforms with stock, not from `snapshots.length` (found 2026-08-17)**
`getComparePageData` filters on `listing_count !== null`, which still includes platforms sitting at zero. Cartier Love Bracelet has 8 snapshot rows but only 4 platforms actually carrying listings, so "8 Sites Compared" would be a false claim in the SERP. Filter on `(listing_count ?? 0) > 0` for anything user-facing.

**`Reveal.tsx`'s scroll animation used to ship content at `opacity:0` in the server-rendered HTML itself (fixed 2026-08-21)**
Every below-the-fold landing section (compare grid, price-check demo, alerts, flip calculator, feature grid, testimonial, CTA) was wrapped in `app/components/landing/Reveal.tsx`, which set `opacity: shown ? 1 : 0` with `shown` starting `false`. Since this is an inline style computed from client state that also renders during SSR, the *server-rendered HTML* — not just a client flash — had those sections at `opacity:0` until an `IntersectionObserver` fired on real scroll. A full-page screenshot, a bot, a slow/no-JS client, or the AI-citability scanner's crawl simulation all see a page that's mostly hero and blank space; the geo-optimizer audit independently flagged this as a "hidden text / cloaking pattern" negative signal, which is the same mechanism from the crawler's side. **Fix: never gate opacity on `shown`.** Content stays `opacity:1` always; only `transform: translateY()` animates on reveal, so the settle-in motion survives but nothing is ever invisible. Verified via Playwright: `getComputedStyle(el).opacity === '0'` count on load went from 7 large sections to 0. If you add a new scroll-reveal effect anywhere, opacity (or `display`/`visibility`) must never be the gated property — animate transform only.

**All root layout `<title>` metadata gets `· Crawli` appended (found 2026-07-09)**
`app/layout.tsx` defines `title: { default, template: "%s · Crawli" }`. Any child page/post that sets its own `title` string gets `· Crawli` (9 chars) auto-appended by Next.js — this is easy to forget when checking a title against Bing's ~60-char limit. Always check the *rendered* `<title>` (`curl -s <url> | grep -oE '<title>.*</title>'`), not just the raw frontmatter/string value. Blog post frontmatter titles should stay ≤51 chars so the rendered title (with suffix) stays ≤60.

## Relevance filtering

**`tshirt` as anchor kills results (fixed 2026-06-29)**
Users type "bape japan tshirt" (one word). Platform titles write "t-shirt" → tokenizes to "shirt" (a stopword). "tshirt" is not in COMMON_WORDS so it becomes an anchor that never matches. Fix: added "tshirt" to `RELEVANCE_STOPWORDS`. If you add more garment-type synonyms to stopwords, keep them as *type* words only — specific items like "puffer" that could narrow results should stay as anchors.

**Compound sleeve-length words (`longsleeve`/`shortsleeve`) as anchors kill results (fixed 2026-07-08)**
Same tokenization gap as the `tshirt` fix above, but titles that write "long sleeve"/"short sleeve" as two words are a real narrowing signal (unlike "shirt"), so it isn't safe to just stopword it — that would let short-sleeve items through on a long-sleeve query. Fixed via `COMPOUND_ANCHOR_FORMS` in `lib/parse.ts`: `anchorSatisfied` checks the one-word query form against a normalized-substring match of the two-word title form (same mechanism as multi-word brand aliases, but a separate small map — deliberately not folded into `queryExpansion.ts`'s `ALIAS_GROUPS`, since that feeds `detectBrandInText` and a non-brand entry there would corrupt brand detection for other queries). Root-caused via a live alert (`black longsleeve messi jersey`, `saved_searches.id=858a5236…`) that had gone ~5 days silently returning 0 new matches every run — `seen_count` never grew past the 2 URLs seeded on first run. If a user reports a search-alert-style query silently returning nothing, check `saved_searches.last_seen_urls` array length over time before assuming the query is genuinely low-volume.

**A brand name that's also an ordinary English word needs a `BRAND_ANCHOR_OVERRIDES` entry, or it silently stops filtering anything (fixed 2026-08-22)**
"acne studios long sleeve" returned generic long-sleeve items from every brand (Zara, Nike, ...), not just Acne Studios. Root cause: `acne`, `studios`, `long`, and `sleeve` are ALL present in `lib/data/commonWords.json` (general English frequency corpus), so none of them qualified as an anchor in `titleMatchesQuery`. With zero anchors, the function falls back to its no-anchor case — "match at least one query token" — and since virtually every long-sleeve listing contains the word "sleeve", the brand was never actually checked. This is the exact blind spot `BRAND_ANCHOR_OVERRIDES` exists to patch, but "acne" was never added to it even though "guess", "polo", "gap", "express", and "balance" — all common English words that are also brand names — already were. Fixed by adding `'acne'`.

**Same-day audit found the identical bug live on 3 more of the app's 33 real `compare_items` brands** — this is not just an Acne-specific issue, it recurs for any supported brand whose defining word(s) are common English. Wrote a script that computed `isAnchor` for every compare-item brand's bare query (no model name) and flagged any with an empty anchor set; then verified each flagged case against a real-brand title (should match) and a same-category different-brand title (should NOT match) before and after the fix. Confirmed broken pre-fix, confirmed fixed post-fix, zero remaining gaps across all 33 brands after:
- `"omega watch"` (no model) matched any brand's watch. Fixed by adding `'omega'`.
- `"ralph lauren shirt"` (no "polo" in the query) matched any brand's shirt. Fixed by adding `'ralph'` **and** `'lauren'` — both, not just one, because "Ralph Lauren" is a two-word phrase where *both* halves are ordinary English words/names on their own. Anchoring only `'lauren'` would still pass an unrelated "LC Lauren Conrad" listing (a real competing brand on these platforms) since AND-logic only requires the one anchored word. Requiring both costs nothing against true positives — a genuine Ralph Lauren listing contains both words anyway — and closes that specific collision. Verified with the "LC Lauren Conrad" title as an explicit negative test case.
- `"north face jacket"` (no "nuptse"/model in the query) matched any brand's jacket. Fixed by adding `'north'` **and** `'face'`, same both-halves reasoning (a lone `'north'` anchor would wrongly pass an unrelated "North Star vintage jacket" listing).

**General rule going forward:** single-word brands or brands with one distinctive word (`'balance'` for "new balance", `'polo'` for "polo ralph lauren", `'essentials'` for "fear of god essentials") only need that one word added. A brand that's a two-(or more-)word phrase where *every* word is independently an ordinary English word needs *all* of them added — anchoring only one reopens a collision with some other real brand that happens to share that single word. **If a user reports a brand query returning results that clearly aren't that brand, check whether the brand's word(s) are in `commonWords.json` and NOT in `BRAND_ANCHOR_OVERRIDES` first** — this is a distinct failure mode from the anchor-AND-logic and stopword issues below (those over-filter; this one under-filters because there ends up being no anchor at all). A quick way to re-run the audit: script `isAnchor(t) = BRAND_ANCHOR_OVERRIDES.has(t) || !COMMON_WORDS.has(t)` over each compare-item brand's bare-query tokens and flag any with an empty result.

**Deep-dive audit (2026-08-22) across luxury/hypebeast/athletic/heritage-denim/mall/outdoor/watch brands added 24 more overrides, and surfaced a mechanism-level limit that no override list can fix**
Went broader than `compare_items` — checked every constituent word of ~80 well-known brand names (Louis Vuitton, Prada, Gucci down through Hollister, PacSun, Uniqlo, Arc'teryx, Rolex) against `commonWords.json`. Most brands were already fine because at least one word in the name is naturally uncommon (`vuitton`, `heuer`, `hilfiger`, `wang`, `mcqueen`, `laurent` all anchor their brand alone despite the other word being generic). Added 24 words for the ones that weren't: `casio`, `tiffany`, `shock` (single distinctive word), plus paired halves for phrases where *both* words are ordinary English — `chrome`+`hearts`, `fear`+`anti`+`social`+`club` (Fear of God / Anti Social Social Club), `stone`+`island`, `under`+`armour`+`armor`, `lee`, `calvin`+`klein`, `american`+`eagle`, `banana`+`republic`, `free`+`people`. Verified with 31 adversarial before/after cases (each "should NOT match" title constructed to contain *exactly one* of the query's common words, e.g. "Roman Armour costume shirt" for a "under armour shirt" query, "Anthropologie dress FREE SHIPPING" for "free people dress") — all 30 fixable cases flipped from matching-everything to correctly excluding the off-brand title, zero regressions against the earlier acne/omega/ralph-lauren/north-face fixes or the 27 `compare_items` brand queries with 2+ words.

**Mathematical limit found: a query that reduces to exactly ONE surviving common-word token cannot be fixed by `BRAND_ANCHOR_OVERRIDES` at all.** For a single-token anchor set, `anchors.every(anchorSatisfied)` and the no-anchor OR-fallback `queryText.some((t) => titleTokens.has(t))` both reduce to the identical check — "does the title contain this one word" — so marking that one word an anchor changes nothing. Proved this with `"columbia jacket"` (tokens reduce to just `{columbia}` since "jacket" is a stopword): both before AND after adding `'columbia'` to the override set, `"Columbia University crewneck jacket varsity"` still wrongly matches. **Left `'columbia'` OUT of the override set** — adding it would misleadingly suggest the query is handled when it provably isn't; the collision is a genuine entity-disambiguation problem (Columbia Sportswear vs. Columbia University) that this mechanism cannot solve. The override only ever helps when a query has **2+ surviving common-word tokens**, which is why e.g. `'lee'` is still worth having despite `"lee jeans"` alone being single-token-unfixable too — a realistic query like `"lee flannel shirt"` has two tokens (`lee`, `flannel`) and does get fixed.

**Three more brands identified as needing a different fix mechanism entirely, not just more override words — flagged, not silently patched:**
- **Old Navy** — "navy" is intentionally in `RELEVANCE_STOPWORDS` as a color and gets stripped before reaching the anchor check at all (by design, so color-word brand collisions don't corrupt color filtering elsewhere). That leaves only `'old'` as a candidate anchor, which is far too generic/collision-prone to add alone (any "old vintage tee" listing would qualify). Needs a dedicated compound-phrase mechanism like `COMPOUND_ANCHOR_FORMS`, not a plain override.
- **Off-White** — same shape of problem, and already a known, deliberate exclusion: `queryExpansion.ts`'s `ALIAS_GROUPS` comment says off-white was left out on purpose because `colorFilter.ts` treats "off-white" as a color, and conflating the two would corrupt color matching. `'off'` alone is also too generic (appears in "% off", "off-shoulder").
- **J.Crew / H&M** — both brands' distinguishing token is a single letter (`j`, `h`, `m`), which `relevanceTokens`' `length >= 3` filter drops entirely before tokens even reach the anchor stage. "j crew" reduces to just `{crew}`, and `'crew'` is a near-universal descriptor ("crew neck") too generic to safely anchor — it wouldn't meaningfully improve precision even if added (see the single-token-limit finding above). "h and m"/"h&m" reduces to zero real tokens once "and" is stripped as a stopword and "h"/"m" are dropped for being too short, meaning the query currently applies **no filtering at all**, not even the flawed OR-fallback. Fixing either needs new tokenization/alias logic, not a `BRAND_ANCHOR_OVERRIDES` entry.

**Brand alias matching is now in `lib/queryExpansion.ts`**
"bape" must match "A Bathing Ape" titles. The static alias map in `queryExpansion.ts` covers well-known streetwear brands. The LLM expansion path (sidecar `/expand-query`) enriches the long tail. `primeExpansion(query)` is called in `searchWorker.ts` before dispatch — this is the only LLM call in the search hot path. Do not add inline LLM calls in `parse.ts` (it's synchronous).

**"japan" is in COMMON_WORDS (~rank 4700)**
So it is NOT an anchor. "bape japan tshirt" → only anchor is "bape". This is correct — "japan" alone should never block a result. Check `lib/data/commonWords.json` before assuming a word is uncommon.

**Anchor-AND logic: all anchors must match**
The old OR logic let Ronaldo jerseys through on "messi jersey" (shared "soccer" token). AND logic was intentional — don't revert. If a user reports too-strict results, the first check is: which token became an unexpected anchor? Is it in COMMON_WORDS? Add it to RELEVANCE_STOPWORDS if it's a garment type.

**Clothing type words must be stopwords**
"shirt", "hoodie", "sneakers", etc. are in RELEVANCE_STOPWORDS. These are too generic to distinguish brand queries. If ThredUp returns garbage for a brand query, first check: is there a clothing-type token slipping through as an anchor?

**A comma-separated alert query could never match (fixed 2026-08-20)**
Same family as the two entries above, but far more damaging. `relevanceTokens` strips all punctuation, so `"bape, supreme, jerseys"` becomes the anchor set `{bape, supreme, jerseys}`, and `titleMatchesQuery` (`lib/parse.ts`) requires a title to contain **every** anchor. No listing is a Bape AND a Supreme AND a jersey, so the alert returned zero forever while still scraping daily. Measured on live data 2026-08-20: **3 of 12 real user alerts were dead for this reason.** Users write alerts as a list because that is the obvious mental model. Fix is **validation, not auto-splitting**: `findAlertQueryProblem` in `lib/alertConstants.ts` rejects `, ; | / & +` at alert creation, enforced both in `CreateAlertModal` and by a zod `.refine()` on `app/api/saved-searches/route.ts` and `[id]/route.ts`. An alert watches one thing. **A comma fan-out was built and deliberately reverted** (owner decision): silently turning one alert into several hides what the product is doing. A tier-aware block message was then also tried and reverted (owner decision, same day): one plain line for every user regardless of tier — "No symbols like X in an alert. Use plain words only." — no per-item suggestion. `findAlertQueryProblem` returns only `{ separators }`. Apostrophes and hyphens are **not** separators — "Levi's" and "wind-breaker" are real searches. **Do not instead make `titleMatchesQuery` OR its anchors** — the ALL-anchors rule is what stops "messi jersey" matching a Ronaldo jersey, and every interactive search depends on it. **Validation guards new and edited alerts only; pre-existing rows keep their unmatchable queries.** Two sibling failure modes remain open (see `docs/planning/AUDIENCE_AND_HOOKS_PLAN.md` F12b): a **non-English query** cannot match English titles, and a **shoe query paired with a clothing size** cannot match because `matchListingSize` tests clothing keys against `CLOTHING_PATTERNS`. Verified by `npx tsx scripts/verify-alert-query.mts` (20 checks).

**A model number in the query was tested against the SIZE in the title (fixed 2026-08-25)**
`titleMatchesQuery` rule 1 rejects a title unless it contains one of the query's numeric tokens — that is what stops `jordan 4` satisfying a `jordan 1` search. It silently assumed every number in a title is a model number. It is not: on platforms whose grid titles are **synthesized from structured attributes** rather than written by a seller, the only number present is the garment size. ThredUp writes `"Levi's Blue Jeans Size 36 waist"` and never writes `501` at all, so `levis 501 jeans` matched **0 of 100 ThredUp rows** — rows ThredUp's own search had just ranked for that exact query. The same bug ran the other way too: a title reading `"Jordan Retro Size 1"` would have satisfied a `jordan 1` search on the strength of its size tag. Fix in `lib/parse.ts`: `nonModelNumerics()` strips size-context numbers (`Size 36`, `Size 26 - 27`, `35 in x 31 in`, `32x34`, `W32 L34`) **and material percentages** (`100% Cotton` — that bare `100` was being read as the model number) out of the title before rule 1 runs. When nothing is left, the title carries no model-number evidence either way and rule 1 **abstains** rather than rejecting; the text anchors still have to match, which is what keeps a `levis` query from returning the RE/DONE jeans ThredUp mixes into the same grid. Measured A/B on identical live rows across all 9 platforms: every delta was **0 to +6 results, never negative**, and a query with no numerics is bit-identical. Verified by `npx tsx scripts/verify-relevance-numerics.mts` (14 checks). **When you add a pattern here, it must be a context that can never be a model number** — a size, a measurement, a percentage. Do not add bare digit ranges.

**A shopper's collapsed spelling could never match a possessive brand — on ANY platform (fixed 2026-08-25)**
Found while fixing ThredUp; independent of it, and the wider of the two. Shoppers type `levis` / `victorias` / `chicos`; every marketplace writes `Levi's` / `Victoria's` / `Chico's`, which `relevanceTokens` splits into `levi` + a bare `s` that it then drops for being under 3 chars. So the anchor could never be satisfied by the brand's own listings. Measured on live Poshmark + ThredUp rows, counting only titles written in the apostrophe form: **`victorias secret bra` 0 of 20, `chicos jacket` 6 of 99, `dillards blazer` 0 of 4, `levis 501 jeans` 0.** After the fix: 100% on all four.

The fix is a **token-level rule in `anchorSatisfied`**, not per-brand aliases: an anchor ending in `s` (length > 3) also matches when the normalized title contains `` `<stem> s` `` as standalone tokens — which is what an apostrophe normalizes to.

**Requiring the apostrophe is the whole safety argument.** It matches "Victoria's Secret" but NOT "Victoria Beckham", a different real brand on the same sites. A bare-stem rule (`victorias` → `victoria`) would conflate them. Two things were tried and rejected:
- **`ALIAS_GROUPS` entries per brand** (`['levis','levi']` was actually written, then removed). Those feed `detectBrandInText`, so `victoria`/`children`/`macy` as surface forms would corrupt brand detection for unrelated titles, and retailer names (Macy's, Kohl's, Dillard's) are not brands at all. Same trap the `COMPOUND_ANCHOR_FORMS` comment already warns about.
- **Stripping a trailing `s` from every token in `relevanceTokens`.** That collapses `vans`→`van`, `hearts`→`heart`, `essentials`→`essential` and would break several real brand anchors in `BRAND_ANCHOR_OVERRIDES`.

Note the sites also carry the collapsed form (sellers type "Macys", "Levis") — those already worked and still do; this only recovers the apostrophe half.

**Vestiaire's brand title-casing mangled possessives (fixed 2026-08-25)**
Same *visible* symptom as the ThredUp entity bug, different mechanism, found by auditing whether ThredUp's defects applied elsewhere. Vestiaire ships brands ALL CAPS and `extract_vestiaire_grid` title-cased them for display, but Python's `str.title()` uppercases the letter after **any** non-alpha character: `"LEVI'S".title() == "Levi'S"`. 15 of 15 rows on `levis 501 jeans` rendered as `"Levi'S 501 straight jeans"` in the results UI. Fixed with `_vestiaire_title_case()`, which repairs only a lone trailing `S` after an apostrophe — deliberately **not** a blanket lowercase-after-apostrophe, because `str.title()` gets `O'Neill` and `L'Occitane` right and a broader rule would break them back to `O'neill`/`L'occitane`. Matching was never affected (both forms tokenize identically); this was purely what the user saw.

**The ThredUp entity/brand-duplication bug is ThredUp-only — audited, don't go looking for it elsewhere (2026-08-25)**
Checked all 9 grid extractors after fixing ThredUp's `Levi&apos;s Levi's ...` titles. **Zero occurrences on any other platform** across 3 entity-prone brand queries (apostrophes and ampersands). The reason is structural and worth knowing before you audit again: BeautifulSoup decodes character references in both `get_text()` **and** attribute values, so entities can only survive where JSON is `json.loads`-ed out of a `<script>` tag — the site HTML-escaped the string before embedding it, and no HTML parser ever touches it. That is ThredUp (JSON-LD) and in principle TheRealReal/Grailed/Mercari (`__NEXT_DATA__`), which do unescape their title fields. Depop and Vestiaire also prepend a brand to the title, but read it via `get_text()`, so their containment checks compare like with like and were clean.

## Platform-specific gotchas

**Never give eBay's search render a `wait_for` (2026-08-25)**
eBay's SRP (`/sch/i.html?_nkw=`) is **server-rendered** — all ~81 `.su-card-container` cards are in the HTML at `domcontentloaded`. It is the only platform in `_build_run_cfg`'s search-page block with no `wait_for`, and that is deliberate. A `wait_for` cannot help (there is nothing to hydrate) and it is how a *walled* page fails: the selector is never satisfied, so an Akamai interstitial burns the full `SEARCH_WAIT_FOR_TIMEOUT_MS` (20s) before the Firecrawl fallback even starts. Stacked under `scrapeSearchPageViaSidecar`'s 60s abort **and its second attempt**, one 403 cost ~100s end-to-end and made a 9-platform search *slower* than the old Avenue B path it replaced. With no `wait_for`, a blocked page returns in ~3s with an empty grid, which `/scrape-search`'s empty-grid branch already routes to Firecrawl (eBay is in `FIRECRAWL_FALLBACK_PLATFORMS` for exactly this). The trade: if eBay ever moves the SRP to CSR, every render silently yields an empty grid and falls through to Firecrawl — the `[ebay-grid] no su-card-container elements found` warning is the signal.

**eBay's SRP class names are `su-card-container` / `s-card__*`, NOT `s-item__*` (2026-08-25)**
Any eBay scraper you remember from the `s-item__title` era matches **zero nodes** — eBay migrated off that class family. Two further traps in the current markup: (1) every SRP seeds **exactly 2 promo tiles** that look like real cards but point at placeholder item id `123456` with a `Shop on eBay` title, an `ir.ebaystatic.com` house image and a fake `$20.00` — let them through and they drag the price average down; (2) `.s-card__title` contains a visually-hidden `.clipped` span, so `get_text()` on the title node yields `"…JacketOpens in a new window or tab"`, which then fails relevance anchoring downstream. Select the inner `.su-styled-text`. Also: the card href carries a per-impression `itmmeta`/`itmprp` tracking payload, so the same listing dedupes as two different URLs across searches (and churns `last_seen_urls` on every alert run) unless you canonicalize to `https://www.ebay.com/itm/<id>`.

**ThredUp's JSON-LD brand is HTML-escaped but its `name` is not (fixed 2026-08-25)**
`extract_thredup_grid` prepends `brand.name` to the title when the title doesn't already contain it. `name` was being run through `html_module.unescape()` and `brand.name` was not, so `"Levi&apos;s"` never matched `"Levi's ..."`, the escaped form got prepended to a title that already had the brand, and the raw entity was **visible in the results UI**: `"Levi&apos;s Levi's Blue Jeans Size 36 waist"`. Measured on `levis 501 jeans`: **85 of 100 rows affected**. Unescape both sides before any containment check — this bites every apostrophe brand (Levi's, Lands' End, Victoria's Secret).

**Sold data lives in a different layer than the live grid — don't add `sold` to the scrapers** (2026-08-10)
Sold comps for Grailed and Poshmark do NOT go through the Python sidecar at all. Both are plain HTTP from TypeScript (`lib/soldComps/`), ~1s each, no browser. Specifics that will otherwise cost hours to rediscover:
- **Grailed:** the `/shop` grid is active-listings-only and its Sold toggle is **login-gated** — `?sold=true` is parsed into Next.js query state but never switches the Algolia index, and clicking the checkbox logged-out fires no request at all. Sold data is a separate Algolia index, `Listing_sold_production`, which answers to the `public_search_key` embedded in every shop page's SSR HTML. Hits carry `sold_price` (true final), `sold_at_i`, and `created_at_i`. If Grailed rotates the key we recover by re-reading it from the page on a 403 — see `lib/soldComps/grailed.ts`.
- **Poshmark:** `availability=sold_out` works, **but you must also pass `sort_by=recently_sold`.** The default sort returns sales up to 6.6 years old (median 203 days), which makes the median meaningless. `sort_by` is validated server-side — a nonsense value returns **zero rows**, which is how to test whether a sort param is real rather than silently ignored. Parse `window.__INITIAL_STATE__.$_search.gridData.data[]`, **not the DOM**: sold cards render differently and the grid selectors find only 27 of 48 rows. `max_id` is a 1-indexed page cursor.
- **Mercari:** `itemStatuses=2` is the sold filter (`status=sold_out` is ignored). Cards carry a SOLD badge and the final price as the first `$` in `ProductThumbItemPrice`. **There is no sale date anywhere in the card DOM or `__NEXT_DATA__`**, so days-to-sell is impossible. Also needs a browser render. Dropped from sold comps for that reason.
- **ThredUp has no sold filter.** `availability=sold` is silently ignored (119 items back, 114 in-stock, 5 incidentally sold). Ruled out 2026-08-10 — do not re-probe without new evidence.
- **Never pool sold medians across platforms.** For "nike air jordan 1", Grailed's sold inventory is adult pairs (median $125) and Poshmark's is mostly youth sizes and Mid/Low models (median $33). The pooled figure ($55) describes neither market. Report per platform.

**Mercari raw-403s but renders in a real browser — do NOT re-add it to the probe**
Mercari's raw HTTP 403 on the datacenter IP does NOT predict native browser failure — same as Depop. Verified 2026-06-29 on the prod Hetzner IP: real Chromium rendered ~3/4 of searches; the rest fell back to Firecrawl. It was wrongly in `FIRECRAWL_PROBE_PLATFORMS`, which made the fast 403 probe skip the working native render and pay Firecrawl on EVERY search. The probe was removed (default now empty; `/opt/crawli/.env` sets `FIRECRAWL_PROBE_PLATFORMS=`). Mercari now runs native-first with Firecrawl fallback. Do NOT re-add it (or any platform) to the probe unless its block also defeats the real browser from the datacenter IP.

**Depop is NOT probed**
Depop's block is fingerprint-based: raw HTTP 403s but the real browser often passes. Probing would force paid Firecrawl over a working free path. Depop stays on try-native-then-fallback.

**Depop CSS Modules prefix rotation — a "block" can actually be a stale selector (found 2026-08-15)**
A user reported "bape t shirt" — normally reliable — suddenly returning 0 Depop results. First hypothesis (reasonable, given the "fingerprint block" entry above) was an anti-bot soft-block: `result.success` stayed `True`, the page was a real 200, `wait_for` was satisfied, but `extract_depop_grid` found 0 cards. That pattern is genuinely ambiguous from the crawl4ai layer alone — a real block and a stale selector look identical. Live diagnosis (dumped the actual HTML via a temporary debug branch in `/scrape-search`, since the failure didn't reproduce in isolated one-off scripts, only through the app) found the real cause: Depop shipped a build where the CSS Modules scoping changed from `styles_productCardRoot__<hash>` to `styles-module__<hash>__productCardRoot` (same shift for `brandName`/`sizeAttributeText`) — the *position* of the hash relative to the semantic name changed, not just its value, so `[class*='styles_productCardRoot']` stopped matching even though 24 real `/products/` links were present in the page. Fixed by matching on the semantic suffix only (`[class*='productCardRoot']` etc., no prefix) — see `extract_depop_grid`'s docstring in `search_page_extractors.py`. **Lesson: when a search-page extractor that was reliably `✅ Working` suddenly returns 0 despite `result.success=True`, check the raw HTML for the expected content before assuming it's the documented anti-bot block — a platform's own frontend rebuild can produce the exact same symptom.** Also added, as general hardening rather than the fix for this specific bug: `main.py`'s pool crawler now periodically recycles (`SIDECAR_POOL_RECYCLE_AFTER_REQUESTS`/`_SECONDS`, default 25 renders / 30 min) and clears cookies on the Depop/Mercari context after every search-page render, and a success-but-empty-grid result on those platforms now force-recycles the pool member and retries once via Firecrawl before giving up — covers the real soft-block case this was originally suspected to be, in case it recurs independently of the selector bug.

**A full-platform audit (2026-08-15) after the Depop fix found the identical bug on Vinted**
Checking every native platform live after the Depop fix above (`grailed`, `mercari`, `thredup`, `vestiaire`, `vinted`, `poshmark`, `stockx` all re-tested with a real query) turned up the same failure mode on Vinted: `extract_vinted_grid` used exact-token dot-selectors (`div.new-item-box__container`, `a.new-item-box__overlay`) and Vinted's build now glues its scoping prefix directly onto the class with **no separating space** — `class="ItemBox-module-scss-module__NoC3Da__new-item-box__container"` is a single token, so the dot-selector (exact-token match) stopped matching even though the substring is right there in the attribute. Different mechanism from Depop's rotation (Depop's prefix changed entirely; Vinted's got a prefix glued onto an unchanged suffix with no delimiter) but the same fix: switched both selectors to `[class*=...]` substring matching, which survives either kind of rotation. **Poshmark's extractor (`tile-grid-redesign__*`) uses the identical brittle exact-token dot-selector style and is currently working — not touched, since it isn't broken, but it's the same latent risk if Poshmark ever glues a prefix the same way.** Grailed/Mercari/ThredUp/Vestiaire/StockX/Poshmark all confirmed returning real results as of this audit.

**ThredUp fires fine with raw HTTP probe but you must NOT probe it**
Same reasoning as Depop — raw-403 from ThredUp does not predict native browser failure.

**Vestiaire is CSR with ~8s hydration**
The `wait_for` selector on Vestiaire needs the full `a[data-cy^="catalog__productCard__"]` — if you change this, the extractor will get empty HTML. `page_timeout=60_000` is necessary.

**StockX is also heavy CSR**
`[data-testid="ProductTile"]` needs 12s+ wait. `page_timeout=60_000`. If the testid changes (StockX deploys regularly), extraction silently returns 0 listings.

**Poshmark/StockX grid cards lazy-load images — must scroll before capturing HTML**
Both platforms swap in the real `<img>` only when a card scrolls into the viewport (IntersectionObserver). `wait_for` only confirms the *first* card exists, so any card below the fold gets captured mid-lazy-load: Poshmark leaves `src` empty (real URL sits in `data-src`), StockX leaves `src` pointing at its own placeholder (`Product-Placeholder-Default-*.jpg` — the gray-X graphic). `main.py`'s `_LAZY_IMAGE_SCROLL_JS` runs as `js_code` (executes after `wait_for`, before HTML capture) to scroll the page and trigger every card's lazy-load first. If you touch the Poshmark/StockX `_build_run_cfg` blocks, keep `js_code` wired — removing it silently brings back missing/placeholder images on every card past the first screenful.

**RealReal is disabled — do not re-enable without a proxy solution**
PerimeterX press-and-hold blocks all headless approaches including UndetectedAdapter + managed profile cookies. The extractor code is scaffolded in `search_page_extractors.py` but `NATIVE_PLATFORMS` in `lib/types.ts` excludes it. The Python `SEARCH_PAGE_PLATFORMS` includes it — so you'd also need `main.py` wait_for config and to uncomment `lib/types.ts`.

**SEARCH_PAGE_PLATFORMS is duplicated**
The set lives in BOTH `crawl4ai-service/search_page_extractors.py` AND `lib/scraper.ts`. Keep them in sync. If a platform is in the Python set but not the TS set, Next.js routes it through Avenue B (Firecrawl) while the sidecar doesn't know to extract its grid.

**`PLATFORM_STRATEGY[platform]` in `lib/firecrawl.ts` is now inert for all Avenue A platforms**
The route checks `SEARCH_PAGE_PLATFORMS.has(platform)` first. The entries are kept as fallbacks in case a search-page extractor breaks later. Do not delete them.

**Homepage schema's `PLATFORMS` array (`app/components/StructuredData.tsx`) is a fourth, separate platform list**
It's hand-maintained and had drifted — missing ThredUp, describing the site as "eight marketplaces" instead of nine, while the same page's `FAQPage` schema (from `faqData.ts`) correctly said nine. Google can flag mismatched entity counts across a page's own JSON-LD. Fixed 2026-07-08; if the platform roster changes again, update this array too (it's independent of `NATIVE_PLATFORMS`/`SEARCH_PAGE_PLATFORMS`/`PLATFORM_NAMES` in `lib/types.ts`).

**`/compare/[slug]` price schema must be `Product`+`AggregateOffer`, not `ItemList`+`Offer`**
`ItemList` renders as a list/carousel rich result in Google, not the price-range/product snippet. Switched 2026-07-08 (`app/compare/[slug]/page.tsx`) to `Product` with a top-level `AggregateOffer` (`lowPrice`/`highPrice`/`offerCount` across all platforms) containing per-platform `Offer` children. If you add more compare data fields (ratings, images), they go on the `Product`, not the old `ItemList`.

## Payments + Supabase

**Five public files duplicate the pricing matrix and nothing keeps them in sync — audit all of them on every tier change**
A tier change is never just `lib/tierCaps.ts` + the pricing page. These AI/answer-engine-facing files each restate plans, caps, and what is free vs paid, and none of them import anything:
- `public/.well-known/ai.txt`
- `public/ai/summary.json`
- `public/ai/service.json`
- `public/ai/faq.json`
- `public/llms.txt`

Plus `app/components/landing/faqData.ts` (feeds both the visible FAQ and the FAQPage JSON-LD) and `docs/reference/B2B_FEATURE_TRUTH.md`.

**Found 2026-08-18: all five had drifted past the 2026-08-17 repackaging.** They still advertised the retired `max` tier at $30/month as purchasable, listed the old free caps (2 alerts, 50 tracked), omitted ThredUp from the platform list, and — worst — `faq.json` asserted "the flip margin calculator is available on all plans including free", which the paywall had made **false**. These files are exactly what AI answer engines read when someone asks what Crawli costs, so a stale number here gets quoted back to prospects as fact. Grep before you finish:
```
grep -rniE "searches per week|per week|\$30|max tier|alerts" public/ app/components/landing/faqData.ts
```

**`nativeResultsCap` is a display slice, not a fetch limit — raising it costs nothing, and it never reaches eBay**
Easy to assume "Pro gets 100 results per platform" means Pro searches cost more than Free's 8. It does not. `lib/searchWorker.ts` calls `scrapeSearchPageViaSidecar(platform, query, 100, 2, signal)` with a **hardcoded 100 on every tier**, then applies `.slice(0, nativeResultsCap)` to what came back. The scrape is identical for every tier; the cap only decides how much of an already-paid-for result set gets returned. Consequences to keep straight:
- Raising `nativeResultsCap` up to 100 is free. Raising it *past* 100 is not — that requires changing the sidecar's limit argument, which costs render time.
- The cap never touches eBay. eBay is non-native so it takes the other branch, which is hardcoded to `filtered.slice(0, 10)` listings, and Firecrawl URL discovery is a hardcoded `const searchLimit = 20` in `lib/firecrawl.ts` with **no tier parameter anywhere in the call chain**. Since eBay is the only platform that always costs money, this means **tier has no effect on marginal search cost at all** — only search *count* does.
- Don't reach for `nativeResultsCap` as a cost lever. It isn't one. Model COGS off search volume and the eBay attach rate (~47% of searches select eBay as of 2026-08-18).

**Marketing copy and enforced caps are allowed to diverge on Pro — but only in one direction, and it carries obligations**
Saves, tracked listings, searches, results depth, and alert count all read "Unlimited" on `/pricing` while `TIER_CAPS.pro` enforces 500 / 500 / 50-per-week / 100-per-platform / 25. This is deliberate (documented at the top of `app/pricing/PricingCards.tsx` and in `lib/tierCaps.ts`): the numbers are anti-abuse backstops set well above the busiest behaviour ever observed, not felt limits. If you touch any of them:
1. **Never let a paid user hit a wall that says they are out of something, or tells them to "upgrade your plan"** — Pro is the top plan, so that copy is nonsense to them. `/api/search`'s and `/api/saved-searches`'s 402s both branch on tier for exactly this reason and log `[quota] PAID user hit the ... abuse backstop`. Any new paid-tier gate needs the same treatment.
2. **If a real user ever lands on one of these caps, raise the cap or drop the word.** Do not leave "Unlimited" standing over a limit somebody actually reached.
3. Lowering any of these caps toward reachable territory means the pricing copy has to change in the same commit.
4. **Not every "Unlimited" cap is free to raise, and it's worth knowing which kind you're looking at before assuming the next one is too.** `nativeResultsCap` really is free at any value — it's a post-fetch `.slice()`, the fetch cost is fixed regardless of the number. Alert count is not that: each saved alert is a *permanent recurring job* (re-runs daily forever via the `/api/cron/run-alerts` crontab), so raising `maxSavedSearches` is cheap-per-unit and linear, not zero-cost. Both still qualified for the "Unlimited" treatment because real usage is nowhere near either backstop — check the actual numbers (searches, cron capacity, whatever the resource is) before assuming a cap generalizes from one case to the next.
5. **A cap enforced from the `profiles` row (not derived live from `TIER_CAPS`) needs a one-time backfill for existing accounts when you raise it.** `max_saved_searches`, like `max_searches_per_period` and `native_results_cap` before it, is written once at subscription time by the Stripe webhook and then read from the row — raising `TIER_CAPS.pro` alone does nothing for an account whose row was written under the old number. Check `select ... from profiles where subscription_tier = 'pro'` before declaring the change live; `verify-paywall.mts`'s "every profile matches its tier caps" check catches a missed one.

**The sold-comps paywall only ever appears where there is real data to withhold — a placeholder-everywhere version was built and reverted same day**
Settled 2026-08-18 after two rounds. Round one made `SoldCompsLockedPanel` render on every query including ones with zero completed sales, backed by a `fakePlaceholderSoldStats()` helper that invented a fake sample size to decorate the empty case. Round two reverted it: the panel (and `PriceSummary`'s inline sold-comps sub-block) now render — blurred — only when `sold.available` is true, i.e. at least one real completed sale exists on either platform (this already covers thin platforms with just 1-2 sales, no median required — see `toLockedResult`). A query with zero sales gets the plain "not enough completed sales" note, worded **identically for free and Pro**, unblurred, no upgrade prompt. `fakePlaceholderSoldStats()` was deleted in the same session; if you're tempted to rebuild it, read the owner's own words first: "if not enough results, it shows the not enough results stuff regardless of user being premium or not but if there's actually results we paywall it and show it so the user can see a difference." A paywall over a query that has nothing behind it converts someone into a refund the moment they upgrade and search it again — don't manufacture urgency you can't deliver on.
Do keep the one thing that survived from round one: `fakeSoldStats()` still passes the real `n`/`windowDays` through unfaked (never secret) and only invents price/spread/days-to-sell — that part was correct before this whole detour started and never changed.

**`MIN_SAMPLE` gates the aggregate, never the rows — and it has a hard floor of 5 for a mechanical reason**
Two different things live in the sold-comps payload and they are gated separately on purpose. `platforms` (median, p25-p75, days-to-sell) is a **claim** — "this sells for $X" — so it needs `MIN_SAMPLE` behind it. `sales` (the individual completed sales) is **evidence** the reader judges for themselves, so it carries no floor at all; a query with 2 sales returns 2 rows and no median. Don't "fix" a thin query by lowering the floor — add rows.
And do not take `MIN_SAMPLE` below 5. `trimPriceOutliers()` returns its input untouched when `comps.length < 4`, so any floor under that publishes an **unfenced** median where a single bundle listing or fat-fingered price sets the answer. 5 keeps the Tukey fence live in every case that reaches it. It was 10 until 2026-08-18; the evidence for 5 is in HANDOFF's entry for that date.

**Adding a field to a cached payload does not update the rows already in the cache**
`sold_comps_cache` holds a raw jsonb `SoldCompsResult` with a 24h TTL, so for a full day after `sales` was added, every cache hit returned a payload with no `sales` key while TypeScript insisted the field was non-optional. The cache-hit path in `/api/sold-comps` normalizes (`sales: payload.sales ?? []`) rather than invalidating — a pre-existing entry is still a perfectly good aggregate. Any future field added to that payload needs the same treatment, and any client reading it should tolerate the field being absent regardless of what the type says.

**A tier gate that fails closed will flash the paywall at paying users unless the loading state is its own branch (hit for real 2026-08-18)**
`useTier()` starts at `null` and `PriceSummary` treated `null` as "not unlocked", so it rendered `LockedOverlay`. That is correct as a data guarantee and wrong as UI: `SearchSection` sets `results` to `null` on the stream's `start` event, so **`PriceSummary` unmounts and remounts on every single search**, and a Pro user got an "Upgrade to Pro" panel for the length of the `/api/billing/status` round trip, every time. Two rules for any new gated surface:
- Fail closed to a **neutral skeleton**, not to the paywall. Three states, not two: unknown / locked / unlocked. The skeleton still renders no real figure, so nothing about the security property changes.
- `useTier` now memoises the resolved tier at module scope (`lastTier`) and seeds `useState` from it, so a remount inside the same page session resolves synchronously. The 30s `inflight` reset still lets a later mount re-check after an upgrade.

**A paid panel that renders `null` when its data is empty is indistinguishable from a broken one**
`SoldCompsPanel` returns `null` on `platforms.length === 0`, and `PriceSummary` rendered it bare. So for a Pro user the sold-comps region showed nothing at all while `/api/sold-comps` was in flight (a separate request that lands seconds after the listings), and nothing at all when a query legitimately had under `MIN_SAMPLE = 10` comps — which reads as "the feature I paid for is missing". `PriceSummary` now renders explicit loading / not-enough-sales / failed-to-load notes in that slot, the same three states `SoldCompsLookup` has carried since `/price-check` shipped. Related: `useSoldComps` seeds `loading` from the query rather than `false`, because the effect that sets it runs after first paint and any caller keying an empty state off `!loading && !data` would flash it for one frame.

**RLS alone is not enough**
Every public table also needs explicit `GRANT SELECT/INSERT/UPDATE/DELETE ON public.<table> TO authenticated, service_role`. Without GRANTs, every request returns Postgres `42501 permission denied` — not a helpful error message. This applies to any new table you create.

**Hit for real 2026-08-15: `watchlist`, `saves`, `collection_folders`, `search_history` all missing `service_role` grants.** `watchlist` had only `REFERENCES/TRIGGER/TRUNCATE` for `service_role` — no CRUD — since whatever migration created it never ran the GRANT. `app/api/billing/status/route.ts` counts tracked listings via the admin (service_role) client and hit `42501` on every settings/profile page load; the count silently fell back to `?? 0` so the bug looked like "tracked count always shows 0," not a crash. Check Postgres logs (`query_logs`, source `postgres_logs`, filter `event_message like '%<table>%'`) — the `log_attributes['parsed.hint']` field spells out the exact `GRANT` needed and `parsed.user_name` confirms it's `authenticator` switching to the denied role. `saves`, `collection_folders`, and `search_history` had the identical gap but were dormant (nothing queried them via the admin client yet). All four fixed via migration granting full CRUD to `service_role`. Ran `select table_name, bool_or(privilege_type='SELECT') ... from information_schema.role_table_grants where grantee='service_role' group by table_name` across every public table to confirm no others were missing grants — `profiles` is the one intentional exception (no INSERT/DELETE for service_role; profile rows are created by a DB trigger on `auth.users`, not app code). If a new table's admin-client reads/writes start 42501ing, check `information_schema.role_table_grants` for that table before assuming it's an RLS policy bug — and run that audit query whenever a new table is added, not just when something breaks.

**RLS scopes ROWS, never COLUMNS — a self-service UPDATE policy is a privilege-escalation hole (found + fixed 2026-08-15)**
`profiles` had the textbook policy `USING (auth.uid() = id)` for UPDATE plus a plain table-level `GRANT UPDATE ... TO authenticated`. That combination is **not** "users can edit their own profile" — it is "users can set any column on their own row." Because `NEXT_PUBLIC_SUPABASE_ANON_KEY` ships to every browser, any logged-in user could call PostgREST directly, bypassing the app entirely:
`PATCH /rest/v1/profiles?id=eq.<own-uid>` with `{"subscription_tier":"pro","search_credits":999999,"searches_used_this_period":0}` — granting themselves paid tier and wiping their own quota counter. No app code was involved or at fault; every billing/quota/onboarding write already went through `createAdminClient()` (service_role) correctly.
Fix was column-scoping the grant to exactly what the one user-scoped writer (`PATCH /api/profile`) touches:
`REVOKE UPDATE ON public.profiles FROM authenticated;` then `GRANT UPDATE (display_name, bio, avatar_url) ON public.profiles TO authenticated;`
**The earlier 2026-08-15 grants audit above did not catch this** — it checked whether `service_role` was *missing* privileges (things breaking), not whether `authenticated` had *excess* ones (nothing breaks, which is exactly why it survived). When a table mixes user-editable fields with billing/quota/entitlement fields, table-level `GRANT UPDATE` is always wrong. Audit with:
`select grantee, string_agg(column_name,', ') from information_schema.column_privileges where table_name='<t>' and privilege_type='UPDATE' group by grantee`

**Grants on `profiles` are COLUMN-level, so a new column arrives with NO grant at all (hit 2026-08-17)**
A consequence of the column-scoping fix above that bites the *next* person, not the person who made it. Because the 2026-08-15 fix issued `GRANT SELECT/UPDATE (col, col, ...)`, PostgREST recorded 24 individual column privileges rather than one table-level privilege. `ALTER TABLE profiles ADD COLUMN max_saves` therefore produced a column that `authenticated` could not read at all — it does not inherit anything, and the failure is a 42501 on any select touching it, not a null. Any migration adding a column to `profiles` must ship its own grants in the same migration:
`grant select (new_col) on public.profiles to authenticated;` plus `grant select (new_col), update (new_col) on public.profiles to service_role;`
Do **not** re-add a table-level grant to "fix" this — that reopens the privilege-escalation hole. Entitlement columns get `service_role` only. Check with the `information_schema.column_privileges` query above; a correctly-added cap column shows 25 columns for `authenticated` SELECT and 24 for UPDATE, not 25/25.

**A cadence/quota floor checked on POST is not checked on PATCH (found 2026-08-17)**

Found while briefly gating free alerts to weekly; **the gate was then reversed (free keeps daily) but both fixes were kept**, because the floor is a tunable dial and leaving its enforcement half-implemented is how it breaks silently next time. **When adding an entitlement check to a create endpoint, grep for every other route accepting the same field.** The PATCH check only fires when the value actually *changes*, so alerts grandfathered onto a faster cadence keep working until their owner touches that field. **A worktree with a symlinked `node_modules` breaks Turbopack dev, intermittently and confusingly (found 2026-08-17)**
Git worktrees keep their own copy of `package-lock.json`, so `next dev` (Turbopack) sees two sibling lockfiles — this repo's and the worktree's — and auto-detects the wrong workspace root (it picked the main repo, not the worktree actually being served). That mismatch corrupts the RSC debug/source-map info Turbopack attaches to modules, which showed up as a dev-only, hard-to-reproduce crash: `TypeError: frame.join is not a function` inside React's owner-stack builder, triggered by an unrelated console.error (a stale Supabase refresh-token cookie) elsewhere in the tree. **Two fixes, both required:** pin `turbopack: { root: __dirname }` in `next.config.ts` so root detection is never ambiguous, **and** give the worktree a real `node_modules` (`npm ci`) instead of symlinking it to the main repo's — once `root` is pinned, Turbopack's filesystem-boundary check hard-rejects a symlink pointing outside it (`Symlink [project]/node_modules is invalid, it points out of the filesystem root`), so the symlink-for-disk-space trick some worktree setups use is incompatible with Turbopack once this is fixed properly. If a fresh worktree's dev server throws bizarre, non-reproducible internal Next/React errors, check `node_modules` isn't a symlink before chasing anything else.

**`search_history` row counts are NOT search counts (found 2026-08-10)**
`search_history` upserts on the unique index `search_history_dedupe (user_id, query, platforms, filters)`. A user running the *same* query with the *same* platforms and filters does not add a row — it only bumps `searched_at`. So `count(*) group by (user_id, query)` counts **distinct platform/filter variants**, not repeats, and it is easy to read "5 rows for one query" as "searched 5 times." It isn't: the busiest pair in the table had 5 rows and 4 distinct platform combos. **The table has never recorded how many times a search was actually run, and there is no way to recover that history.** Treat any "user searched X N times" claim sourced from this table as wrong unless it is counting variants on purpose. A `search_count` column + `record_search()` RPC were built to fix this forward and then reverted the same day (product decision — the repeat-intent feature they existed for was dropped), so the gap is open by choice, not by oversight.

**supabase-js `.insert()`/`.update()` never throws — an unchecked call can fail silently forever (found 2026-07-15)**

**Baseline-invalidating alert edits now wipe `notifications` too, not just `alert_matches` (2026-07-15)**

**Unlimited alerts is safe against dollar cost — the real ceiling to watch is cron drain time, not spend (2026-08-18)**
When Pro's `maxSavedSearches` cap was raised and marketed "Unlimited" (8 → 25, see HANDOFF's 2026-08-18 alerts entry), the dollar-cost side was already confirmed at $0 marginal — `ALERT_EXCLUDED_PLATFORMS` excludes eBay, the only Firecrawl-metered platform, from every alert run, so raising this cap never moves the Firecrawl bill regardless of count. Checked Resend separately via the Resend MCP (`list-emails`): **44 emails sent total across the whole app since 2026-07-20** (~29 days), roughly 1.5/day including signup confirmations — trivial against any Resend tier, free or paid.

At today's scale (13 total alerts, 1 Pro account) this is a complete non-issue. It would only start to matter if Pro adoption grew into the hundreds of users each holding many alerts, at which point one timezone's 9 AM cluster could take longer than 15 minutes to fully drain — some users' daily email landing a bit later that morning, not a failure. If Pro signups start climbing for real, this is the metric to watch (time to drain the 9 AM batch), not Firecrawl spend or Resend volume — check `/var/log/crawli-alerts.log` for how many ticks a morning's batch takes before assuming any change is needed.

**`nextAnchoredRunAt` ignored `cadenceHours` until 2026-06-30**
`lib/alertSchedule.ts`'s `ANCHOR_HOURS` was `(_cadenceHours) => [9]` — the param was accepted but never used, so the function only ever found "the next occurrence of 9 AM" regardless of cadence. This produced correct daily behavior by coincidence (24h cadence = next-9AM is always right), but adding weekly (168h) would have silently fired it daily too. Fixed by computing a `daySpan = Math.round(cadenceHours / 24)` and rolling forward that many days before landing on 9 AM, instead of branching on hour-of-day alone. Lesson: a function whose parameter is silently unused is a landmine for the next cadence value — grep for params before assuming "it already handles N" just because the signature accepts N.

**Auth emails (signup confirmation / reset) are throttled by TWO Supabase limits, not Resend (investigated 2026-07-11)**
Confirmation + reset emails go through Supabase Auth → custom SMTP (Resend, verified `thecrawli.com`), NOT the app's `resend.emails.send` code paths (those are contact form / alerts only). So "slow confirmation email" is almost never a Resend problem — Resend delivered every one. Two Supabase-side throttles cause it: (1) **project-wide email rate limit** (Auth → Rate Limits → "Rate limit for sending emails") — was the default **30/h shared across ALL auth email types**; raised to **100/h** on 2026-07-11. Configuring custom SMTP does NOT auto-raise it. (2) **per-user ~60s resend cooldown** — re-submitting signup within the window logs `user_repeated_signup` and **silently sends no email** (200 response, nothing sent), which reads as "email never arrives." Bot signups (e.g. `radiant-flow.org`, random gmails) burn the hourly budget because **CAPTCHA is disabled** (Auth → Attack Protection). Real ceiling on Free tier is Resend's **100 emails/day / 3000/month** — that's what to upgrade if volume grows, not Supabase. For a *single* slow signup (few emails, cap not hit), suspect Gmail Promotions/spam + young-domain deferral, or the 60s no-op — not the cap. The check-email page now has a resend button with a matching 60s countdown so users stop re-hitting signup into the no-op.

**`signUp`'s `identities:[]` response is ambiguous — don't infer confirmation status from `resend()`'s success/error (fixed 2026-07-11)**
When `supabase.auth.signUp()` is called for an email that already has an account, it returns `data.user` with `identities: []` regardless of whether that account is confirmed, unconfirmed, or has no password identity at all (e.g. Google-only signup). The old code tried to disambiguate by calling `supabase.auth.resend({type:'signup', email})` and branching on whether it errored — but `resend()` **also** returns 200 success (silent no-op) for already-confirmed accounts, as part of the same anti-enumeration design. So the "resend errored → show already registered" branch was effectively dead code; real users with existing (especially Google-only) accounts always got funneled into a "check your email" screen that would never receive anything. Confirmed via `auth.users` lookup: a user's account showed `email_confirmed_at` set at creation with `confirmation_sent_at: null` (Google OAuth auto-confirms, no confirmation email ever sent) — he then tried email/password signup twice, `/resend` returned 200 both times, no email arrived either time, and he only recovered via "Forgot password" (which doubles as a way to attach a password identity to an OAuth-only account). Fix: `app/login/page.tsx` no longer branches on `resend()`'s result — it always routes `identities:[]` to `/check-email?...&existing=1`, and that page shows both "if new, check your email" AND concrete recovery options (Continue with Google, sign in with password, forgot password) since the two cases can't be told apart client-side. The resend button stays visible in the `existing=1` state too (a genuinely-unconfirmed repeat-signup user still needs a manual resend path) — don't hide it behind `!existing`, that was an earlier draft bug caught before merge.

**Verified via `auth.users`/`auth.identities` SQL (2026-07-11), for anyone re-deriving this:** `signUp()` on an existing account is a true no-op — no row is created or mutated, confirmed by re-running it against a real Google-only account and diffing `auth.identities` before/after (unchanged, single `google` row). `auth.users.updateUser({ password })` on an OAuth-only account (the password-reset flow) DOES set a working `encrypted_password` on the existing `auth.users` row — confirmed for the real incident user (`has_password` flipped `true` at the exact reset timestamp) — but does NOT add a corresponding `auth.identities` row with `provider: 'email'`. So after a reset, the account has one `identities` row (`google`) but two working sign-in methods (Google + password) — don't assume identity count reflects sign-in method count when debugging this area.

**`profiles` column DEFAULTs drift from `TIER_CAPS.free` when pricing changes (found 2026-07-17, actually fixed 2026-07-23)**

**Signing out re-runs list-loading effects, and the resulting 401 toasts "Could not load ..." at the user (fixed 2026-08-25)**
Reported live: clicking sign out worked, but a "Could not load tracked listings" toast rode along to the landing page. Chain: `AppShell.handleSignOut` calls `supabase.auth.signOut()`, which fires `onAuthStateChange`; `WatchlistProvider` and `SavesProvider` both `setSignedIn(false)`; their `hydrateUrls` is `useCallback(..., [signedIn])`, so flipping that state gives the callback a **new identity**; every list effect that lists `hydrateUrls` in its dep array then re-runs and refetches **after the session is already gone**, gets a 401, and its catch fires a toast. The component has not unmounted yet (`router.push('/')` is async) and the Toaster is top-level, so the toast survives the navigation. Three loaders had it: `WatchlistTab.tsx`, `SavesTab.tsx`, `SavesPageClient.tsx`. Fix: guard with `if (res.status === 401) return;` **before** the `if (!res.ok) throw` in each loader. **The auth layer is the single owner of session messaging** (`AppShell` shows "Your session expired" and deliberately suppresses even that for an intentional sign-out via `consumeIntentionalSignOut()`), so a data component must never editorialize a 401. General rule: **a provider callback whose `useCallback` deps include auth state is not stable across sign-in/sign-out**, so any effect depending on it will refire at exactly the moment its request cannot succeed. Either guard the 401 (done here) or keep the callback identity stable behind a ref. The folder loaders (`SavesTab`/`SavesPageClient` `reloadFolders`, `MoveToFolderModal`) do **not** have this bug only because they are mount-only and don't depend on `hydrateUrls`, so if you ever add auth-derived deps to those, add the same guard.

**Fire-and-forget `fetch()` in a client component reports to Sentry as an unhandled production error (fixed 2026-08-25)**
Sentry issue `37a35af8` on `/alerts?tab=search`: `TypeError: Load failed` at `AlertsTabsClient.tsx:36`, Mobile Safari only, `handled = no`, `mechanism = auto.browser.global_handlers.onunhandledrejection`. That line was `void fetch('/api/notifications/mark-seen', { method: 'POST' })` with no `.catch()`. **"Load failed" is WebKit's generic message for a fetch that fails at the network layer, not a JS bug**, and it is Safari's equivalent of Chrome's "Failed to fetch". The effect runs on mount, so if the user backgrounds Safari, navigates away, or hits flaky mobile data mid-request, WebKit aborts the request, the promise rejects, and with no handler attached the rejection reaches `window.onunhandledrejection` where Sentry captures it as a high-priority unhandled error. The request itself failing is harmless here (it only clears the bell badge, and the next visit retries), so the whole defect is a benign failure being reported as a crash. **Rule: any `fetch()` whose result nobody awaits must handle its own rejection**, `void fetch(...).catch(() => {})` for genuinely fire-and-forget calls, and an async IIFE inside `useEffect` needs `try`/`catch`, not `try`/`finally`. Two more instances of the same defect were on the same route: `SearchAlertsTab.tsx` used `try`/`finally` with no `catch` (rejection escaped even though `finally` cleared loading), and `AlertMatchesPage.tsx` had both an uncaught `mark-seen` call and an uncaught `Promise.all` of three fetches whose rejection **also left the page skeletoning forever**, because `alert` stayed `undefined` and the render treats `undefined` as still-loading. Note the second-order lesson there: an unhandled rejection in a loader is never only a Sentry problem, it is also a stuck loading state, so the catch must resolve the UI into a real terminal state (that page now has a `loadError` branch). Do **not** silence this class by adding "Load failed" to `ignoreErrors` in `instrumentation-client.ts`, unlike the two entries already listed there this one is fixable in application code and a blanket ignore would also hide genuine fetch failures elsewhere. Sweep for regressions with `grep -rn "void fetch(" app lib | grep -v "\.catch"`.

**Mobile horizontal overflow comes from `justify-between` label/value rows, not the page shell**
The page shells (`mx-auto max-w-* px-6` + nav) are all mobile-safe; public pages never overflow. Offenders are inner `flex items-center justify-between` rows where one side can't shrink: a long unbroken string (email — needs `break-all`), a fixed-width control (`w-48` quota bars), or a `shrink-0` text run (the profile recent-search platform list) colliding with a sibling. Fix pattern: stack the row on mobile (`flex-col gap-… sm:flex-row sm:items-center sm:justify-between`), give the text side `min-w-0`, and either `break-all`/`truncate` long strings or `hidden sm:inline` secondary text. Detect by loading at 360px and checking `document.documentElement.scrollWidth > clientWidth` — `scrollWidth` over viewport = real overflow; per-element `right > vw` inside an `overflow-x:auto`/marquee container is by-design (Hero search chips, platform logo marquee). Protected pages need auth to view; a throwaway routable page (NOT `_`-prefixed — Next treats `_dir` as private/404) rendering the real prop-driven components with worst-case data verifies them without logging in.

**...unless a `sr-only` absolutely-positioned input has no positioned ancestor (fixed 2026-07-09)**
`FilterPanel.tsx`'s platform-chip row (`overflow-x-auto`, `flex-nowrap`) was making the *whole page* horizontally scrollable on mobile — not just the chip row. Root cause: each chip `<label>` wraps a `<input class="sr-only">` (Tailwind's `position: absolute` screen-reader-only pattern) for the checkbox. The `<label>` had no `position: relative`, so the checkbox's containing block bubbled all the way up to the initial containing block (the document), and its static position was computed from its location in the row's *unclipped* content width (844px), not the row's visible clipped box — pinning a 1px invisible element up to ~450px past the viewport edge and inflating `document.documentElement.scrollWidth` to match. Fix: add `relative` to the label wrapping any `sr-only` absolutely-positioned input, especially inside an `overflow-x-auto`/`flex-nowrap` row. The same unwrapped pattern exists in `app/(protected)/settings/page.tsx`'s platform checkboxes but doesn't currently trigger it because that row is `flex-wrap` (reflows instead of overflowing) — same fix if it's ever changed to `flex-nowrap`. Detect exactly like the note above (`scrollWidth > clientWidth` at 360–390px), but when the offending elements are all `sr-only`/1px and `position: absolute|fixed`, look for the nearest ancestor `label`/wrapper missing `position: relative` rather than assuming a layout-width bug.

**Bare markdown `<table>` elements also blew out mobile width on 47 blog posts (fixed 2026-07-09)**
`globals.css` has `.blog-content .table-wrapper { overflow-x: auto }`, but `lib/blog.ts` rendered posts with plain `marked.parse(content)` — the default renderer emits a bare `<table>` with zero wrapper, so that CSS rule matched nothing. **Sentry `NotFoundError: The object can not be found here.` on mobile Safari is browser noise, not an app bug (triaged 2026-08-15)**

`/crawl4ai-service/venv` matches only that exact directory. A sibling backup like `venv.bak-stale-path` is *not* covered, so a `git add -A` swept 13,609 files (761MB) into a commit, and the push was rejected by GitHub for a 113MB `patchright/driver/node` binary over the 100MB file limit. Entries are now `/crawl4ai-service/venv*` and `/python/venv*`. Recovery when this happens: `git reset --soft <last-good-sha>` (keeps all real work staged, loses nothing), then `git restore --staged <venv-dir>/`, then fix the ignore pattern — do **not** reach for `git filter-repo` or a force-push, since a rejected push means the objects never reached the remote.

**sidecar TTL caches**
- `/scrape` (per URL): 30 min TTL
- `/scrape-search` (per `platform::query`): 10 min TTL
- `_expand_cache` (query expansion, per normalized query): 7 day TTL
- Only successful, non-empty results land in cache; failures retry next time.

**n8n on the server is the real edit path**
`n8n MCP` tools are read-only and only see a subset of workflows. All real workflow edits go via SSH. See `docs/reference/SERVER_REFERENCE.md` for the SSH workflow edit pattern. After editing: export → patch → import + `--active=true` → `systemctl restart n8n`.

**n8n `Run on demand` trigger is required for CLI testing**
n8n 2.8.4's `n8n execute --id` fails with "Missing node to start execution" unless the workflow also has an `Execute Workflow Trigger` node (not just the schedule trigger). Add one to any workflow you want to CLI-test.

**Server deploy `npm install` needs `unzip` (fixed 2026-06-29)**
Puppeteer's postinstall downloads Chrome and extracts it with `unzip` — if missing, install fails with "Required native binary ... was not found in PATH". Already installed on the production box via `apt-get install -y unzip`; only relevant again on a fresh server. If `npm install` instead fails with "browser folder exists but executable is missing," a prior failed extraction left a stale partial cache — `rm -rf /root/.cache/puppeteer && npm install` to fix (upstream extract-zip bug, see `docs/reference/SERVER_REFERENCE.md`).

**Only one Sentry client entry point: `instrumentation-client.ts` (fixed 2026-07-08)**
Next.js auto-loads root `instrumentation-client.ts` — it needs no import anywhere. The original Sentry install (commit `5f9f39b`) also left a legacy `sentry.client.config.ts` wired in via `app/sentry-provider.tsx`, so Sentry was initializing twice per pageload with two different, conflicting configs (the stale one ran `tracesSampleRate: 1` + `sendDefaultPii: true` unconditionally, overriding the intended prod value of `0.1`). Confirmed via a real `next build`: `.next/static/chunks/*.js` contained both configs' distinctive strings in one ~204 KB chunk — this is very likely what PageSpeed Insights was flagging as "~188 KiB unused JavaScript" on the homepage. Removed `sentry.client.config.ts` and `app/sentry-provider.tsx`; the conservative settings (env DSN, `tracesSampleRate: 0.1` in prod) now live solely in `instrumentation-client.ts`. If Sentry needs client config again, edit that file only — do not reintroduce `sentry.client.config.ts` or a wrapper component that imports it.

**Onboarding gate is blocking and lives in `(protected)/layout.tsx`.** While
`profiles.onboarding_completed_at` is null, every protected route redirects to
`/onboarding`. `/onboarding` is deliberately **outside** `app/(protected)/` so it
cannot catch itself — moving it inside creates an infinite redirect that locks every
user out of the entire app. Any new step added to the flow must advance even when its
upstream call fails, for the same reason. `OnboardingFlow.tsx`'s own back navigation
(`prevStep()` in `lib/onboarding.ts`) is safe against this because it never persists —
it only moves local `step` state, so closing the tab mid-back-navigation still resumes
at the furthest step actually reached via `onboarding_step`, never at a stale local
position.

**Any link rendered inside an onboarding screen must open in a new tab.** A plain
`<Link>` to any `(protected)/*` route (e.g. `/settings`) navigates the current tab away
from `/onboarding`, and since the destination is itself gated on
`onboarding_completed_at`, a user who hasn't finished yet gets bounced straight back to
`/onboarding` — silently discarding whatever they'd typed into that step's local state
(e.g. a buy-price value in `TailStep`/`SoldCompsLookup`). `SoldCompsLookup.tsx`'s
"See the fee breakdown" link to `/settings#platform-fees` uses `target="_blank"
rel="noopener noreferrer"` for exactly this reason — it's shared with the onboarding
tail step, not just the standalone `/price-check` page where a same-tab link would be
fine.

**Inserting a new step into `ONBOARDING_STEPS` shifts what every already-persisted
`onboarding_step` index means for anyone currently mid-flow.** `stepFromIndex()` in
`lib/onboarding.ts` resumes purely by array position — it has no concept of "the step
after alert," only "index 4." Adding the `name` step between `branch` and `seed`
(2026-08-20) meant every in-progress user's saved index silently pointed one screen
later than where they actually were. Fixed with a one-time migration resetting
`onboarding_step = 0` for every profile with `onboarding_completed_at IS NULL AND
onboarding_step > 0` at deploy time. **Any future step insertion (not append) needs the
same migration**, scoped to profiles that haven't completed onboarding yet — completed
profiles never read `onboarding_step` again so they're unaffected either way.

## Content / marketing

**No em/en dashes in any caption or slide**
The platform rule: no em dashes (—), en dashes (–), or punctuation hyphens used as sentence separators. Use line breaks or plain commas instead. This applies to all generated content in `docs/marketing/`.

**Obfuscate commercial intent in TikTok content**
No `thecrawli.com`, no URL, no "search Crawli", no "download", no "link in bio" on any slide or caption. Crawli is teased as a subtle aside on the final slide only, worded differently each post, present in only some posts. Goal is comment inquiries not clicks. This is baked into the live n8n content brief (`moMVEnr5L6kGgJTC`).

**visual-history.json and POSTS_README.md are the source of truth for batch history**
Before generating a new carousel batch: run `marketing-visual-diversity` skill to read `check-visual-diversity.js` output. Each batch must differ from the last 1-2 on font pairing AND text placement AND layout. These are in `docs/marketing/visual-history.json`.

**Zernio Threads posts: `content` is NOT optional even when using `threadItems`**
`docs.zernio.com/platforms/threads` claims top-level `content` is "optional if threadItems provided" — false as of 2026-07-06. A `threadItems`-only request 400s with `"Content is required for selected platforms"`. `content` must always carry the root post; `platformSpecificData.threadItems` holds only *additional* reply post(s) in the chain, not a repeat of the root. See `scripts/post-to-threads.mjs` and `docs/planning/AGENT_PLAN.md` §1H.

**Threads' 500-char cap can't be bypassed via Zernio**
Zernio does not expose Threads' native 10,000-character text-attachment feature at all — don't build anything assuming it can. Longer content means a real Threads reply (a second post), not a workaround.

**GSC zero-click anomaly on a well-ranked page isn't always a title problem — check cannibalization first**
Before assuming a bad title/snippet caused 0 clicks despite decent position, run `mcp__gsc__cannibalization` to rule out two pages competing for the same query first (would otherwise misdiagnose the fix). Confirmed clean via `dimension_filters` on `page` scoped to the exact query on 2026-07-06 before rewriting two post titles.

**Blog post `description` frontmatter must be ≤160 chars, not just `title` ≤60**
`description` drives `<meta name="description">`, `og:description`, AND `twitter:description` simultaneously (`app/blog/[slug]/page.tsx`) — one over-long field breaks all three surfaces at once. Bing Webmaster flags anything over ~160 chars as "too long." Found 2026-07-06: 66 of 89 posts had descriptions over 160 chars (up to 340) because the reframe session's title-length rule was never paired with an equivalent description rule. Check with: `python3 -c "import re,glob; [print(len(re.search(r'^description:\s*\"(.*)\"\s*$', open(f).read(), re.MULTILINE).group(1)), f) for f in glob.glob('content/blog/*.md')]"` and flag anything outside 25-160.

## LLM / sidecar

**OpenAI node output shape in n8n**
The output path is `output[0].content[0].text`, not `message.content`. This has bitten multiple sessions. Verify with the MCP tools or live execution before wiring up an AI node.

**LLM expansion is fire-and-forget for the first request**
`primeExpansion(query)` is awaited in `searchWorker.ts` which means it blocks the search until expansion resolves (or times out at 5s). The timeout is intentional — first-request latency is bounded. Subsequent searches for the same query hit the in-memory cache instantly.

**Do not add per-listing LLM calls**
The only LLM calls in the search hot path are: (1) expansion via `/expand-query` (once per unique query, cached 7d), (2) Tier 2 fallback extraction when Tier 1 structured fails. Adding LLM calls per-listing would make a 9-platform search cost $0.009 × 90 listings = $0.81/search. Check COGS before adding any new LLM call.

**DeepSeek V4 models burn heavy hidden reasoning tokens on small extraction tasks — tested 2026-08-13, not recommended as primary provider**
`_PROVIDER_KEY_ENV` in `main.py` was missing a `"deepseek"` entry — any missing key silently resolves to `None` (the same sentinel `ollama` uses for "no key required"), so `resolve_llm()` would skip reading `DEEPSEEK_API_KEY` entirely rather than validating it. Fixed (added the mapping). But live A/B testing (`deepseek/deepseek-v4-flash` vs `openai/gpt-4o-mini`, same real listing pages, same prompts/schema) found DeepSeek is **not a straight upgrade despite its lower headline per-token price**: it generates 5-20x more output tokens (`reasoning_tokens` in the usage payload) even on trivial JSON-schema extraction, which made it ~21% more expensive on `/scrape` Tier 2 extraction and ~5x more expensive on `/expand-query` in practice, plus 1.5-4x slower wall-clock. On `/expand-query` specifically it twice exceeded the endpoint's 12s timeout in a 4-query sample (would silently degrade to empty enrichment in prod, per the fire-and-forget behavior above). Tried `reasoning_effort="low"` and `thinking={"type":"disabled"}` — neither reduced reasoning-token volume for this provider via litellm; if DeepSeek is revisited, this needs a provider-specific fix (not just a `LLM_PROVIDER` swap) before it's viable for latency-sensitive calls. Extraction accuracy itself was on par with gpt-4o-mini (5/5 correct prices across StockX/Poshmark test listings).

**Carousel exports are 2x retina by design — archives get big, and that is not a bug to "fix" in the exporter**
`docs/marketing/export-slides.js` sets `deviceScaleFactor: 2`, so a 1080x1350 slide lands on disk as 2160x2700 (~2-5MB each). That is intentional (platforms downscale a 2x source more cleanly than they upscale a 1x one). The cost is that batch archives grow fast: as of 2026-08-19 `docs/marketing/` held 622MB, dominated by `dated-marketing-folders.zip`. Two things to know before touching any of it. (1) **Zipping does nothing.** PNG is already compressed, so that archive was at 3% compression ratio; the zip is a container, not a saving. Real reduction comes only from downscaling or re-encoding the images themselves. (2) **Marketing images are gitignored and therefore backed up nowhere.** They are excluded by `docs/marketing/**/*.{png,jpg,jpeg,webp,gif,mp4,mov}` and `docs/marketing/*.zip`, so git is not a safety net. Copy anything irreplaceable off-machine before bulk-editing it. A 2026-08-19 pass downscaled archived exports to the 1080x1350 spec (622MB to 356MB) — that was a one-time cleanup of already-posted batches, and **new batches will export at 2x again**, by design. Do not lower `deviceScaleFactor` to keep the folder small without deciding that upload quality matters less than disk.
